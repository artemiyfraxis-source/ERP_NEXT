# Гибрид закупок и склада: ERP_NEXT + Roller_Buyer (стенд Вити)

Ветка `vitya/hybrid`, только локально, проверяется на стенде (`%USERPROFILE%\ERP_NEXT-stage`, `stage.ps1 up -Ref vitya/hybrid`).
Каждое изменение — **опция** с переключателем «Было / Новое» (подвал меню → «Опции стенда», переключает администратор).
На проде опций нет: без `ERP_STAGE_OPTIONS` всё выключено и код ведёт себя как в `main`.

## Сравнение блоков

| Блок | ERP_NEXT сейчас | Roller_Buyer | Решение для гибрида |
|---|---|---|---|
| Закупки: поток | Строка закупки (~80 полей) проходит этапы Новый → В работе → Жду счёт → В оплату → В пути → Карантин → Готово; много закупщиков, очереди, «Мои позиции» блоками | Заявка → запрос КП → КП → решение → счёт → оплата → УПД → приход; статус **вычисляется** из фактов | Основа — ERP (многопользовательский, в проде). Из Roller берём то, чего в ERP нет: «Сегодня», историю цен, показатели, затем сравнение КП |
| Сравнение КП | Один КП-файл на заказ (`kp.py`), сравнения нет | Матрица поставщиков, цена с НДС (`grossUnit`), покрытие потребности с учётом MOQ/упаковки/ступеней, «ворота» ≥3 КП с причиной обхода | Волна 2 (нужны таблицы КП) |
| Показатели закупщика | Нет | Экономия к базовому КП, в срок к обещанной дате, сроки этапов, качество, рейтинг поставщиков | Волна 1: что считается из уже имеющихся фактов ERP. Базовое КП — после волны 2 |
| Склад | Партии ГРН, баланс = приход − списано, резерв; правка строки меняет количества напрямую; поиск — подстрока, все партии в памяти | Партии ГРН + журнал движений со знаком, баланс = сумма движений, минус невозможен, отмена последнего движения, поиск по словам | Модель ERP оставляем (живой склад). Волна 1: поиск по словам, количества только движениями |
| Реестр УПД | Нет: номер/дата УПД копируются в поля каждой строки приёмки | Реестр документов, своя и распознанная версии, проверка, привязка к счёту, приход из УПД | Волна 2: реестр входящих документов (УПД + счета) поверх строк приёмки |
| Номенклатура | Нет мастер-таблицы: позиция = текст, копируемый по цепочке; два несвязанных набора типов | `items` + `item_aliases` (как поставщик называет позицию, учится на каждой привязке), карточка позиции с историей цен | Волна 3 (самая дорогая: связать строки заявок/закупок/склада) |
| Справочники / поставщики | Поставщик = текст; справочник «домен → поставщик» перезаписывается целиком | Поставщик с ИНН, категориями, «ключевой», карточка и рейтинг | Волна 2: справочник поставщиков с ИНН, строки закупки сопоставляются по имени |

## Опции

**Волна 1 — без изменения схемы БД (собирается сейчас)**
- `procurement.today` — «Сегодня» закупщика.
- `procurement.price_history` — «Покупали ранее».
- `procurement.kpi` — показатели закупщика.
- `warehouse.word_search` — поиск по словам.
- `warehouse.strict_quantities` — количества только движениями.

**Волна 2 — новые таблицы (миграции только в ветке, база стенда своя на ветку)**
- `references.suppliers` — справочник поставщиков (ИНН, контакты, ключевой).
- `receiving.documents` — реестр входящих документов (УПД/счета), без дублей.
- `procurement.quotes` — сравнение КП с ценой с НДС и «воротами».

**Волна 3** — `items.master`: номенклатура и названия у поставщиков.

Фактически сделано к 12.10 (список опций — `backend/app/shared/stage_options.py`, панель «Опции стенда»):
`requests.form`, `procurement.today`, `procurement.price_history`, `procurement.history`, `procurement.kpi`,
`procurement.rfq`, `procurement.dense`, `projects.internal`, `references.suppliers`, `references.items`,
`warehouse.word_search`, `warehouse.strict_quantities`, `warehouse.scan`, `warehouse.undo`, `ui.dark_theme`, `ui.search`.

**Волна 4 — блок закупки и документы из Roller_Buyer целиком (13.10, миграция `0124_purchasing_documents`)**
- Данные: `python -m app.modules.purchasing.rb_import --snapshot <копия buyer.db> --data-dir <DATA_DIR> [--apply]` —
  поставщики (без нашего ИНН 5040191181), номенклатура, названия у поставщиков, справочные цены, реестр УПД (Google и
  ЭДО) со строками и файлами, счета Kaiten с позициями, платёжками и файлами, решения «счёт ↔ УПД». Файлы — в базе
  (`purchasing_document_files`, как все вложения ERP). Повторный запуск обновляет, правки, сделанные в ERP, не трогает.
- `documents.upd` — «УПД»: реестр, карточка со строками и файлом, правка шапки, «Проверено», дубли, ИНН продавца с
  исправлением OCR, привязка к поставщику, загрузка XML/ZIP из Диадока, «Продавцы без поставщика».
- `documents.chain` — «Счета», «Цепочка документов», «Поиск по документам»: счёт → платёжка → УПД → приёмка ERP по номеру
  УПД → партии; связи считаются при чтении, хранится только слово закупщика (подтвердил / отклонил).
- `references.price_book` — справочные цены и цены из УПД в карточке позиции, УПД и счета в карточке поставщика,
  «Каталог закупок», «Завести позиции из УПД», в пуле запросов КП — «раньше дешевле» по УПД и прайсам.
- `procurement.quote_import` — КП из PDF и текста, КП за упаковку → цена за единицу.
- Не переносится: синхронизация с Google-разбором и Kaiten по сети (ключи живут в Roller_Buyer; данные — повторной
  загрузкой из свежей копии), заказы/приходы Roller_Buyer (в ERP своя приёмка — цепочка доходит до неё по номеру УПД).

## Как принимать
Опция «Новое» прошла тесты → решение «принять» → отдельная маленькая ветка `vitya/<опция>` без переключателя (или с ним) → PR в ERP_NEXT.
«Вернуть» → опция остаётся выключенной, код удаляется из `vitya/hybrid`.
