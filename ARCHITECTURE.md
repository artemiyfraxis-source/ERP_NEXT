# Архитектура Fraxis ERP Next

## Граница наследия

От работающей ERP сохраняем модуль «Проекты»: реестр, карточку проекта,
расчёт и подготовку КП. До нативной замены он работает через совместимый API,
зафиксированный в `contracts/legacy-projects.openapi.json`.

Ни один другой раздел восстановленной ERP не считается эталоном. Заявки,
закупка, приёмка, склад, комплектация, выдача, отгрузка, сотрудники и права
переносятся из действующего SUPPLYMAP по его предметным инвариантам.

## Целевая форма

Первая версия — модульный монолит:

- FastAPI — единый backend и границы модулей;
- PostgreSQL в эксплуатации, SQLite только для локальных тестов;
- React/TypeScript — единая оболочка и страницы модулей;
- транзакционный audit log и outbox для фоновых заданий;
- один модуль владеет своими таблицами и статусами;
- внешние Google Sheets доступны только через переходные адаптеры.

Микросервисы сейчас не нужны: сквозной поток закупки требует общих транзакций,
а независимые сервисы добавят сетевые отказы раньше, чем появится нагрузка,
которая их оправдывает.

## Сквозной поток

`Проект/BOM → заявка → закупка → счёт/оплата → приёмка/ВК → партия ГРН → склад → резерв → выдача в цех → готовая продукция → отгрузка`.

Проект публикует BOM через порт, но не пишет напрямую в таблицы закупки.
Закупка создаёт партии, склад владеет балансом, комплектация владеет резервом,
а выдача проводит списание. Эти четыре действия не должны снова смешаться в
одной функции, как это неизбежно происходило вокруг минутного `OwnerTick`.

## Модули backend

Каждый модуль получает четыре слоя:

1. `domain` — чистые правила и машина состояний;
2. `application` — сценарии использования и транзакции;
3. `infrastructure` — БД и временные адаптеры Google;
4. `api` — Pydantic-схемы и FastAPI router.

Общие слои ограничены идентификацией, БД, аудитом, outbox и наблюдаемостью.
Доменные модули не импортируют router или ORM-модели соседей.

## Порядок переноса

1. Общая идентификация, роли, audit/outbox и контракт проектов.
2. Техкарты из `feat/techmap-web-generator`: чистое Python-ядро переносится
   без Google IO; карточки изделий, выдача ЭТК и append-only ревизии хранятся в ERP;
   нормативные справочники приходят через порт ERP, а библиотека типовых
   операционных карт хранится как атомарно заменяемый снимок с точным commit.
   Сборщик ЭТК читает библиотеку и config внутри одной транзакции, а в проект пишет
   самодостаточный снимок, поэтому позднейшая правка шаблона не меняет уже выданную ревизию.
   Межмодульный workflow обогащает config нормами терминалов из снимка References v14 до входа в домен Techcards;
   так модули не импортируют репозитории друг друга, а в ревизии остаётся метадата исходного снимка.
3. Заявки и закупка — первый сквозной записывающий срез.
4. Приёмка и склад с партиями `ГРН + ПАКЕТ`.
5. Комплектация, выдача и отгрузка.
6. Отключение Google-адаптеров после сверки данных и параллельной эксплуатации.

## Обновляемость

`module-map.json` — машинный список владельцев и исходников. Контракт проектов
обновляется генератором, а не ручным копированием. Для каждого перенесённого
модуля сохраняются ссылки на исходные файлы SUPPLYMAP и тесты инвариантов;
изменение в GAS сначала меняет предметный тест новой версии, затем реализацию.

## Контракт заявок

`requests.domain` не знает о FastAPI, ORM, Google Sheets и модуле проектов.
Проект передаётся как необязательная ссылка `project_reference`; существование и
доступность проекта проверит application layer через порт модуля Projects.

Новая заявка сразу получает `Новый` в той же транзакции, без минутного тика.
Команда закупщика переводит её в `В работе` и создаёт outbox-сообщение. Только consumer
модуля Procurement создаёт закупочную строку `Новый`, ревизия `A`, с уникальным ключом
`request:<uuid>:procurement:v<version>`. Повторная доставка сообщения безопасна;
новая ревизия требует отдельной команды и не затирает прежнюю строку.

`System ID` формата `SM-YYYYMMDD-NN` пока выдаётся для параллельной сверки с
SUPPLYMAP, но UUID остаётся настоящим идентификатором агрегата. В БД генерация
legacy-номера и номера назначения должна сериализоваться уникальными
ограничениями/sequence, а не локом приложения.

Application layer уже определяет транзакционные сценарии создания и handoff
через Unit of Work. Повтор `creation_key` с теми же данными возвращает исходную
пачку, а с другим payload отклоняется. Повтор handoff читает существующее
outbox-сообщение и не создаёт второй audit/outbox. In-memory реализация
существует только внутри тестов и не подключается к FastAPI.

SQLAlchemy-адаптер и первая Alembic-миграция реализуют эти порты. В эксплуатации
движок включается только через `ERP_DATABASE_URL`; автоматического `create_all`
на старте нет. HTTP write API закрыт серверной auth-зависимостью: имя сотрудника
не принимается из тела запроса, handoff дополнительно требует `buyer/admin`.

## Первый контур закупки

`procurement.domain` сам назначает входящей строке статус `Новый` и ревизию
`A`; событие Requests не содержит этих решений. Consumer блокирует очередное
необработанное outbox-сообщение, идемпотентно создаёт строку и в той же
транзакции пишет audit и `published_at`. Отдельный polling-процесс не входит в
HTTP-приложение и может масштабироваться через `FOR UPDATE SKIP LOCKED`.

Взятие в работу разрешено закупщику только из `Новый`. Повтор той же команды
тем же закупщиком ничего не записывает, а захват другим отклоняется. Факты может
редактировать только владелец строки в `В работе`; полный набор готовности
автоматически переводит её в `Готов к запросу`. ORM использует поле `version`,
поэтому конкурентная запись не проходит молча.

Повреждённое integration event не блокирует всю очередь: ошибка фиксируется в
outbox, повтор откладывается с backoff, а после пяти неудач событие переходит в
dead-letter. В лог попадает только UUID сообщения, не его payload.

После заполнения фактов закупщик последовательно фиксирует запрос поставщику,
счёт с ожидаемой датой и оплату. Только переход `В оплату → В пути` публикует
самодостаточное `receiving.expected`; Receiving не читает таблицы Procurement.

### Деньги строки закупки

`procurement.money` — чистый порт `Currency.gs` и `kpApplyCurrencyAndFact_`.

**Поля и пересчёт:**
- Факт-цены: ЦЕНА без НДС, ставка НДС, ЦЕНА С НДС, СУММА.
- Кроме них в строке ВАЛЮТА и реквизиты счёта: НАИМЕНОВАНИЕ (Счет), № и ДАТА СЧЕТА.
- Пересчёт идёт от ведущего поля (`net`/`gross`/`vat`/`qty`/`sum`); без явного поля действует правило КП.
- СУММА = ЦЕНА С НДС × КОЛ-ВО, каждое производное значение округляется до копеек.
- Инвалюта: каждая сумма × курс ЦБ (`Value/Nominal`) × 1,065, после чего ВАЛЮТА становится RUB.
- Числа принимаются так, как написаны в счетах: «1 234,56», «1,234.56».

**Гейт `PUR_PAY_REQUIRED`** (документ по качеству не входит, потому что `ENFORCE_QUALITY_DOC=false`):
- требуемые поля: ВАЛЮТА, обе цены, КОЛ-ВО и ЕД.ИЗМ (факт), СУММА, НАИМЕНОВАНИЕ (Счет), ОЖИД. ДАТА;
- без них счёт не принимается (`Жду счет → В оплату`);
- тот же гейт повторяется на оплате (`В оплату → В пути`). Строки, ушедшие в оплату до денежного блока,
  не оплачиваются, пока закупщик не допишет деньги; править их можно в `Жду счет` и `В оплату`.

**Намеренные отступления от SUPPLYMAP (решено агентом — проверить у бухгалтера):**
- *Дата курса.* SUPPLYMAP берёт курс на сегодня, в момент ввода. ERP берёт:
  - дату оплаты, иначе ДАТУ СЧЕТА, иначе уже сохранённую дату, иначе сегодня (МСК);
  - курс и дату хранит в строке, и повторное сохранение берёт сохранённый курс ЦБ, так что сумма не плывёт;
  - хранит и исходные суммы в валюте счёта (`source_*`), чтобы при оплате один раз пересчитать
    инвалютную строку по курсу дня оплаты.
- *ЦБ не ответил.* Запрос повторяется, как `withRetry_`: 3 попытки, паузы 0,4 и 0,8 с, только сетевые
  ошибки и 5xx. SUPPLYMAP после этого пишет суммы в валюте как есть. ERP вместо этого:
  - отвечает 409 `manual_rate_required`;
  - закупщик вводит курс вручную, и строка сохраняется с пометкой «курс введён вручную»;
  - следующее сохранение при доступном ЦБ заменяет ручной курс курсом ЦБ той же даты, пересчитывает суммы
    и снимает пометку; в audit остаются оба курса;
  - после оплаты деньги закрыты, поэтому для этого есть отдельная команда
    `POST /api/procurement/{id}/exchange-rate/reconcile`.
- *Округление* — Decimal `ROUND_HALF_UP` вместо JS float `Math.round`. Результаты расходятся только на
  float-артефактах вроде 1.005.
- *Отрицательные суммы* отклоняются. В SUPPLYMAP проверки нет.

## Приёмка и склад

Receiving владеет поставкой и входным контролем. Неверный товар и просрочка
терминальны (`Возврат`), отсутствие документов и устранимые несоответствия дают
`Ожидание/Карантин`, а один лишь излишек принимается по фактическому количеству.
ГРН выдаётся в серии назначения `<prefix>.<YY>.<7 digits>`; неизвестное
назначение требует явного выбора только из `CSM/PPM`.

Принятая позиция не попадает на склад до физического адреса. После размещения
Receiving единожды публикует `warehouse.received`. Warehouse агрегирует по
`склад + ГРН + пакет`, считает `баланс = приход − списано` и отдельно хранит
резерв. Списание не может затронуть резерв или уйти ниже нуля; возврат списания
не может превышать ранее списанное количество.

Идентификатор товара в складской партии — `article`; `name` остаётся отдельным
необязательным описанием, а `series` означает партию изготовителя и не заменяет
наш ГРН. Миграция старых данных копирует прежнее `name` в `article`, поэтому
количественная история и ключ партии не меняются.

Ручной складской ввод требует артикул и предлагает наименование, серию и тип из
уже известных партий и версионного снимка БД.Технология. Распознавание корпусов
и кодов коаксиальных разъёмов выполняется в workflow, который связывает Warehouse,
References и чистый каталог корпусов Techcards; домен количественного учёта от них
не зависит. Подстановка заполняет только пустые поля и не заменяет решение кладовщика.
Старая строка без артикула и наименования остаётся доступной по временному UI-ключу
`ГРН/пакет`, поэтому её можно раскрыть и исправить без изменения партии.

Физический адрес имеет вид `стеллаж + полка A…Z + номер + необязательная ячейка
A…Z`. Перенос всего места выполняется одной транзакцией только внутри одного
склада, сохраняет букву ячейки каждой партии и не затрагивает нулевые остатки.

### Дозавоз `-Д`

Порт `Receiving.gs:80-224`.

**Как возникает:**
- Первый ВК строки (из `В пути`) с недовозом `заказ − УПД > 0` в той же транзакции публикует
  `procurement.backorder_requested` с ключом `receiving:{id}:backorder`.
- Повторный ВК из `Ожидание/Карантин` дозавоз не ставит.
- Procurement создаёт строку `<ID>-Д`: если имя занято — `-Д2`, `-Д3`; дозавоз дозавоза — `<ID>-Д-Д`.
  Признак дозавоза — суффикс `/-Д\d*$/`, как `isBackorderId_`, поэтому миграция не нужна.

**Что попадает в строку `-Д`:**
- копия исходной строки: закупщик, поставщик, цена, НДС, валюта и курс, счёт, `paid_at`;
- количество равно недовозу;
- даты очищены, статус `Согласование`.

**Дальше:**
- Закупщик подтверждает досыл новой ОЖИД. ДАТА → `В пути`. Строка публикует свой `receiving.expected` и
  ждётся приёмкой как обычная поставка, минуя «В оплату»: деньги уже уплачены.
- Отмена (`Отменено`) публикует `requests.reorder_requested`. Requests создаёт новую заявку: тот же
  инициатор и позиция, остаток, новый System ID, ССЫЛКА очищена. Заявка сразу уходит в закупку в `Новый`,
  как строка в SUPPLYMAP.
- В сводке снабжения плана производства строка `-Д` — отдельная позиция.

**Намеренные отступления (решение владельца, 2026-09-28):**
- SUPPLYMAP берёт `parseInt` от недовоза. ERP хранит точный остаток: 2,5 м, а не 2 м.
- SUPPLYMAP копирует СУММУ исходной строки за полное количество. ERP пересчитывает сумму на остаток:
  `ЦЕНА С НДС × недовоз`, до копеек.

## Комплектация и выдача

Fulfillment получает состав производственного комплекта идемпотентной командой
и создаёт заявку независимо от текущего остатка. Пустой состав не создаёт
заявку. Каждая строка отдельно хранит исходную потребность, зарезервированное и
выданное количество; при нехватке одной партии остаток потребности остаётся
отдельной незакрытой строкой с тем же `requirement_id`.

Партия всегда выбирается человеком. Привязка резервирует складской остаток, а
снятие привязки освобождает его в одной транзакции. Только полностью закрытый
комплект можно перевести в `Готов к выдаче`; выдача одним commit списывает все
зарезервированные партии и меняет статус заявки. Ошибка любой строки откатывает
операцию целиком, поэтому частично выданного комплекта не возникает.

После возврата комплекта каждая выданная строка получает явную раскладку:
`годное + брак возвращён + брак не возвращён + израсходовано = выдано`.
Годное количество сторнирует списание исходной партии и при необходимости
перемещает её на новый адрес. Брак хранится в заявке как факт и не увеличивает
доступный остаток; отдельный контур решений по браку появится вместе с
производственной прослеживаемостью.

## Производственные задания

Первый этап production-контура переносит только уже реализованные правила
`ProdTasks.gs`. При запуске задание получает неизменяемый снимок маршрута,
поэтому новая редакция техкарты не меняет ранее выданную работу. Операция может
иметь несколько операторов; подготовка рабочего места учитывается целиком, а
штучное время делится между ними.

Планировщик использует настраиваемую смену цеха: рабочие дни, начало/конец,
перерывы и бюджет эффективных часов; отдельно учитывает праздники, отсутствия и
занятость оператора в других неотменённых заданиях. Матрица компетенций задаёт
допуск, звёзды и коэффициент скорости на код операции. Автоплан строит цепочку
из снимка ЭТК, перебирает передаточные партии 1/5/10/25/100%, подбирает бригаду до
заданного размера и возвращает неулучшаемые варианты по времени первых изделий
и полного завершения. Уже назначенные операции сохраняются, пока мастер явно
не выбрал пересчёт. Ручное пересечение не блокируется, но возвращается мастеру
как предупреждение.

Статус операции не хранится: он вычисляется по сумме неизменяемой годной
выработки. Отмена меняет только статус задания и сохраняет маршрут, назначения и
план как производственную историю.

`Production Plan` — read model над фактами модулей, а не вторая машина статусов. Этап каждой КБ выводится из
фактов выданной ТК, набранного комплекта, запущенного задания, принятой ГП и отгрузки; этап проекта —
самая отстающая КБ. Заявки и закупка формируют сводку снабжения, задания — охват плана. Ручными остаются
append-only комментарий, блокер/снятие блокера, дедлайн, временное переопределение этапа КБ и результат
проверки ТК. Значение `авто` снимает ручной этап; проверка старше текущей ревизии ТК считается
неактуальной. Данные legacy-реестра проектов приходят как атомарно
заменяемая проекция; доменное владение «Проектами» остаётся в legacy.

Исполнение хранится отдельными агрегатами. `WorkSession` фиксирует исполнителя,
входы и паузы; `ProductionOutput` добавляется один раз и не редактируется;
`ConsumptionEdge` связывает расход входной коробки с выходной. При старте
количество резервируется, при записи выработки резерв превращается в расход, а
при отмене сессии освобождается. `ProductionBox` проходит состояния «Открыта» →
«Закрыта оператором» → «Подтверждена» → «Израсходована». Возврат мастером требует
причину и сохраняет присвоенный номер. Номер коробки — шесть цифр, дефис и
контрольная цифра Луна, как в SUPPLYMAP; ручной ввод терпит пробелы, длинное тире
и пропущенный дефис. ERP выдаёт `000001`–`099999`, SUPPLYMAP — от `100000`, поэтому
при параллельной работе номера двух систем не пересекаются. Только подтверждённый
остаток предыдущей операции может стать входом следующей, поэтому UI не является
границей контроля.

Возвращённую коробку («Возвращена») оператор исправляет, как `prodWorkFix_` в SUPPLYMAP. Новая
`ProductionOutput` с `correction_of_id` заменяет одну запись выработки этой коробки. Старая запись остаётся, но
выпадает из всех сумм, в том числе из лимита «не больше задания». Количество коробки заменяется:
было − старые годные + новые. Разница `годные + брак` на этапе > 1 добирается из тех же входных коробок по порядку
или возвращается в них с последней. Возврат пишется ребром расхода с отрицательным количеством, а родословная
показывает чистое количество. Израсходованная входная коробка, в которую вернули штуки, снова становится
«Подтверждена». После исправления коробка сразу «Закрыта оператором» и ждёт мастера. «Доложить» (`reopen`)
остаётся отдельным действием: это новая работа в ту же коробку, и она только прибавляет.

**Исправление коробки — решено агентом, проверить (PX-1, 2026-09-28):**
- Заменяется одна запись, как в SUPPLYMAP (решение владельца). Исправлять можно только действующую запись;
  каждую запись заменяют не больше одного раза (уникальный `correction_of_id`). Если в коробке неверны две
  сдачи, мастер возвращает её ещё раз.
- У записи-исправления нет рабочей сессии (`session_id` пуст) и нет своего времени: начало = конец, пауз нет.
- Годные 0 при браке > 0 разрешены, как в SUPPLYMAP: коробка может уйти мастеру с нулём. Запрет «пустую не
  закрыть» относится только к обычному закрытию.
- Лимит задания при исправлении проверяется на любом этапе, как в SUPPLYMAP; обычная сдача — только на первом.
- Первый этап: списание материала (ГРН) исправление не трогает. В SUPPLYMAP вход первого этапа не двигается, а в
  ERP расход материала не связан с числом годных.
- Порядок входных коробок для добора и возврата: по времени создания входной коробки (в ERP у расхода нет своей
  последовательности).
- Брак (рамки задал владелец): запись Б- не меняется и не удаляется. Если брак в исправлении изменился, при новом
  количестве > 0 заводится новая Б- с характером и описанием, как при сдаче. Прежняя Б- получает
  `replaced_by_output_id`, а её количество, статус и решение остаются. По заменённой Б- решение уже не
  принимается, и из очереди мастера она уходит.

Первая операция запускается только для задания, связанного с заявкой
комплектации в статусе «КБ Выдана». Её входы ссылаются на строки выдачи и
сохраняют ГРН, пакет и количество; активная сессия резервирует доступный остаток,
а завершение добавляет неизменяемое ребро `ГРН+пакет → выходная коробка`.

Последняя подтверждённая коробка передаётся в уже заведённую позицию реестра ГП
одной транзакцией: коробка становится израсходованной, количество увеличивает
`FinishedGood.accepted`, а отдельная запись связывает номер коробки с ГРН `ГП`.
Повторная сдача той же коробки блокируется уникальностью источника.

Брак является отдельным агрегатом, а не отрицательным количеством в годной
коробке. `ProductionOutput.defect_quantity` фиксирует факт, а `DefectRecord`
получает собственный номер `Б-...`, характер, описание и ссылку на выработку.
Решение мастера хранится отдельной append-only записью с актом/основанием;
исходные данные оператора после решения не переписываются.

Серийные номера резервируются на всё количество задания в той же транзакции,
что и запуск. При ОТК свободные номера связываются с последней коробкой:
принятые получают статус «Принято ОТК», отклонённые — «Брак». Сдача в ГП
разрешена только после ОТК и переводит принятые номера в «Сдано на ГП» с ГРН.
Решение мастера по отклонённым ОТК изделиям хранится отдельной append-only
записью с уникальной ссылкой на протокол контроля; исходный протокол и серийные
номера не переписываются.
Количество брака ОТК отдельно уменьшает доступный остаток коробки.

Средства измерения — самостоятельный реестр с датами поверки. Контроль хранит
снимок выбранных ID СИ; доменная проверка запрещает выключенное или просроченное
СИ независимо от интерфейса. ОТК выполняет отдельная роль `qc`, не оператор.

Отчёт родословной — read model поверх четырёх источников рёбер: расход выданных
ГРН, переходы между коробками, привязка серийных номеров и приёмка в ГРН ГП.
Поиск сначала находит любой совпавший узел, затем возвращает всю связанную
компоненту в обе стороны. Алгоритм графа остаётся чистым и не зависит от SQL.

## Готовая продукция и отгрузка

Модуль `shipping` владеет двумя связанными агрегатами. `FinishedGood` — складской
регистр одной КБ проекта; `Shipment` — заявка со снимком адресата и строками,
которые ссылаются на регистр. Запись отбора изменяет оба агрегата в одной
транзакции. Поэтому отмена или возврат строки не могут оставить расхождение
между `finished_goods.shipped` и суммой набранного в заявках.

Количество клиента (`requested`) и складской факт (`picked`) не объединяются:
недобор остаётся видимым и может быть набран после следующей сдачи цеха.
Переходы статусов и гейты УПД/трека принадлежат доменной модели, а не React UI.
PL/DN на этом этапе получают только учётные номера; генератор файлов остаётся за
границей модуля до отдельного переноса шаблонов.

## Справочники

Модуль `references` не смешивает ручные настройки с нормативной базой
техопераций. Три пользовательские карты заменяются атомарно и защищены
уникальностью нормализованного ключа. Это не позволяет одной ссылке поставщика,
одному изготовителю или одному сечению молча получить два разных значения.
Карта «ГОСТ-сечение → AWG» — цеховой справочник СПР.КАБ из SUPPLYMAP; сборка
техкарты передаёт её в подбор сечения под норму обжима. Поправка обжима
1,0 мм² → 18 AWG зашита в коде и сильнее карты, как в SUPPLYMAP.

База `ОП/ОБ/ТЕР/КОАКС` импортируется только полным снимком с `schema_version`,
датой исходника и датой импорта. Поиск читает этот снимок, но не меняет его.
Так смена структуры источника становится явной миграцией, а редактор небольших
карт не превращается в интерфейс ручного исправления тысяч нормативных строк.

## Аудит, задания и уведомления

`audit_events` — append-only доказательный журнал. В отличие от защищённого
Google-листа ему не нужен промежуточный буфер: событие пишется тем же commit,
что и изменение агрегата, а API предоставляет только чтение. Управленческий
экран фильтрует журнал, но не имеет команд изменения или удаления.

Фоновая работа строится на transactional outbox, отдельных идемпотентных
consumer-функциях и dead-letter после исчерпания повторов. `OwnerTick` не
переносится: его синхронизации между листами исчезли вместе с дублированием
данных, а один долгий минутный конвейер снова создал бы голодание хвоста.
Уведомление сначала становится outbox-событием, затем отдельной транзакцией
попадает в персональную ленту; ошибка доставки не отменяет исходную операцию.

## Identity

`identity_users.id` — единственный ключ владения и аудита; ФИО остаётся только
снимком для отображения. Идемпотентность создания заявки ограничена UUID
инициатора, поэтому одинаковые браузерные ключи разных сотрудников не
конфликтуют. Доступ вычисляется как роль плюс персональное перекрытие
`none/view/edit`, причём write API требует именно `edit`, а не просто роль.

Слабая схема SUPPLYMAP `SHA-256(email:PIN)` и токен в `localStorage` намеренно
не воспроизводятся. Новый контур использует Argon2id с параметрами OWASP,
случайный непрозрачный session token в HttpOnly-cookie, отдельный CSRF secret,
лимиты попыток по учётной записи и адресу клиента, скользящий и абсолютный срок
сессии. На каждом запросе активность сотрудника и актуальная матрица прав
читаются заново; деактивация отзывает все сессии.
