# Архитектура Fraxis ERP Next

## Граница наследия

Реестр проектов и «Расчёт и КП» старой ERP (ERP_RECOVERED) вне переноса: это другой блок, им занимается
другой программист (решение владельца 29.09.2026). Legacy-bridge и iframe сняты. «Проекты» ERP — только
производственные проекты, которые заводятся из расчёта (SUPPLYMAP `TcKitset.gs`, модуль techcards, наборы).

Ни один раздел восстановленной ERP не считается эталоном. Заявки,
закупка, приёмка, склад, комплектация, выдача, отгрузка, сотрудники и права
переносятся из действующего SUPPLYMAP по его предметным инвариантам.

## Целевая форма

Первая версия — модульный монолит:

- FastAPI — единый backend и границы модулей;
- PostgreSQL в эксплуатации, SQLite только для локальных тестов;
- React/TypeScript — единая оболочка и страницы модулей;
- транзакционный audit log и outbox для фоновых заданий;
- один модуль владеет своими таблицами и статусами;
- внешние Google Sheets доступны только через переходные адаптеры.

Микросервисы сейчас не нужны: сквозной поток закупки требует общих транзакций,
а независимые сервисы добавят сетевые отказы раньше, чем появится нагрузка,
которая их оправдывает.

## Направление: один проект — один трек (владелец 2026-10-04: «делай как он хочет» — подход Василия Костромина)

Целевая модель, к которой ведём модули после запуска 05.10; текущий код ей не противоречит, переход — надстройкой:
- **Проект — одна головная карточка** и архив всех операций всех модулей, через которые он прошёл. Не два модуля
  и не два способа получить один результат: у менеджеров (расчёт, КП, закупка до «оплачено») и у производства один
  и тот же проект и один трек.
- **Арбитр ERP по триггерам** (смена статуса, событие модуля) раздаёт задачи в нужные модули; последовательный
  результат собирается в карточке проекта — зайдя в неё, видно всё, что по ней создано. Блоки — это задачи, которые
  арбитр ставит модулю, а не отдельные копии проекта. Основа есть: audit log + outbox и `app/workflows`.
- **Полуфабрикаты: 1 операция = 1 полуфабрикат.** Маршрут изготовления — граф (схема): ветки полуфабрикатов
  сходятся в сборку, у операции может быть несколько входов (сейчас — линейная цепочка по `position`,
  `production/execution.py:215`). Так собирается любой жгут, в т.ч. «разъём — разъём» со сложной разводкой.
- **Генератор ТК сшивается с полуфабрикатами:** сначала в генератор добавляется схема-граф и групповые операции
  поверх отдельных — нынешний результат генератора не ломается, это надстройка для интеграций; затем производство
  исполняет граф (планирование сразу по графу, как в прототипе PRODUCTION_PLANNER).
- Порядок: ARCH-TRACK-1 граф и групповые операции в генераторе → ARCH-TRACK-2 производство по графу →
  ARCH-TRACK-3 арбитр задач по триггерам и трек проекта (`docs/migration/BACKLOG.md`). Каждый шаг — с планом и
  согласованием с Василием; концепт-документ Василия (Google Docs) в репозиторий ещё не перенесён.

## Сквозной поток

`Проект/BOM → заявка → закупка → счёт/оплата → приёмка/ВК → партия ГРН → склад → резерв → выдача в цех → готовая продукция → отгрузка`.

Проект публикует BOM через порт, но не пишет напрямую в таблицы закупки.
Закупка создаёт партии, склад владеет балансом, комплектация владеет резервом,
а выдача проводит списание. Эти четыре действия не должны снова смешаться в
одной функции, как это неизбежно происходило вокруг минутного `OwnerTick`.

## Модули backend

Каждый модуль получает четыре слоя:

1. `domain` — чистые правила и машина состояний;
2. `application` — сценарии использования и транзакции;
3. `infrastructure` — БД и временные адаптеры Google;
4. `api` — Pydantic-схемы и FastAPI router.

Общие слои ограничены идентификацией, БД, аудитом, outbox и наблюдаемостью.
Доменные модули не импортируют router или ORM-модели соседей.

## Обновляемость

`module-map.json` — машинный список владельцев и исходников. Контракт проектов
обновляется генератором, а не ручным копированием. Для каждого перенесённого
модуля сохраняются ссылки на исходные файлы SUPPLYMAP и тесты инвариантов;
изменение в GAS сначала меняет предметный тест новой версии, затем реализацию.

**Пин на незапушенный SUPPLYMAP — решено агентом, проверить (DRIFT-lib-bfef60d, 2026-09-28):**
библиотека ТК синхронизирована с `SUPPLYMAP_SOURCE_REF=main` (d2df8b8): в `origin/main` SUPPLYMAP этого
коммита ещё нет. Пины techcards и production указывают на коммит, который появится на сервере после
пуша SUPPLYMAP владельцем; на другой машине без этого пуша архитектурные тесты пинов будут красными.

## Контракт заявок

`requests.domain` не знает о FastAPI, ORM, Google Sheets и модуле проектов.
Проект передаётся как необязательная ссылка `project_reference`; существование и
доступность проекта проверит application layer через порт модуля Projects.

Формат номера — перенос `projNoValid_` / `projNoNorm_` (`Schema.gs`): `<цифры>К[буква]` или
`<цифры>МФ` с сериями и подномерами, старая схема `П<гг><мм>-<n>`; латинская `K` отклоняется,
в заявке хранится каноническая форма («2000к» → «2000К.1»). Существование проверяет
`create_requests` через порт `ProjectRegistry` (аудит RQ-4). Решения агента, **решено агентом —
проверить**:
- Реестр в ERP — снимок проектов, который импортируется для плана цеха
  (`production_plan_projects`); адаптер `app/workflows/project_registry.py`, модуль Requests
  таблиц Production не читает. Открытый проект — не терминальный и не «Закрыт», как
  `purposeProjects_` в `Forms.gs`.
- Пустой снимок (реестр ещё не импортирован) считается недоступным реестром: проверяется только
  формат. В SUPPLYMAP недоступный реестр блокирует проектные назначения; в ERP номер проекта —
  необязательное отдельное поле, и блок до первого импорта остановил бы все заявки с проектом.
- Реестр проверяется при создании заявки (`POST /api/requests`), не в `/validate`: у
  предпросмотра нет транзакции, итоговое решение принимает команда создания. Проект вне
  реестра отклоняет всю пачку с номером позиции, как `submitRequests_`.
- Мягкое предупреждение импорта из расчёта (`Imports.gs`) — `warnings` ответов `/import/calc` и `/import` (RQ-5).

Новая заявка сразу получает `Новый` в той же транзакции, без минутного тика.
Команда закупщика переводит её в `В работе` и создаёт outbox-сообщение. Только consumer
модуля Procurement создаёт закупочную строку `Новый`, ревизия `A`, с уникальным ключом
`request:<uuid>:procurement:v<version>`. Повторная доставка сообщения безопасна;
новая ревизия требует отдельной команды и не затирает прежнюю строку.

**Повторный перенос — решено агентом, проверить (RQ-3/PR-2, 2026-09-28):**
- Отдельная команда — тот же `POST /api/requests/handoff` с флагом `retransfer: true`, только для заявки
  «В работе» (кнопка «Повторно в закупку» с подтверждением). Каждый вызов поднимает версию заявки и даёт
  новое событие `procurement.requested`: повтор кнопки — ещё одна ревизия, как в SUPPLYMAP (там у
  повторного переноса нет защиты от двойного клика). Аудит — `request.resent_to_procurement`.
- Решение о ревизии принимает Procurement, а не Requests: если по `source_request_id` уже есть строка,
  consumer создаёт новую — System ID `nextSystemId_` по номерам строк закупки на день события
  (`SM-YYYYMMDD-NN`, хвост `-Д` считается по ведущим цифрам, как `parseInt`), ревизия — max буква среди
  строк с тем же НАЗНАЧЕНИЕМ + 1 (`nextRetransferRevision_`). Строки дозавоза `-Д` тоже входят в max.
- НАЗНАЧЕНИЕ сравнивается как `normHeader_` в SUPPLYMAP — пробелы схлопнуты, регистр не важен
  (`designation_key`); в SQL это делается в Python, потому что `lower()` SQLite не складывает кириллицу.
  **Решено агентом — проверить (PR-2, 2026-09-29)** — прежнее решение RQ-3 «по точному значению» заменено.
- Номер новой строки, как и в SUPPLYMAP, берётся только из строк закупки, поэтому может совпасть с
  `System ID` ещё не перенесённой заявки того же дня (так же у «Раздробить», PR-9). SUPPLYMAP узнаёт
  «уже перенесено» по System ID и такой заявке даёт новый номер; в ERP первый перенос на занятый номер
  тоже получает свежий `SM-YYYYMMDD-NN`, но остаётся Рев.A — это первая строка заявки (в SUPPLYMAP ревизия
  была бы следующей буквой после занявшей номер строки). Двух строк закупки с одним System ID нет.
  **Решено агентом — проверить (PR-2, 2026-09-29).**

`System ID` формата `SM-YYYYMMDD-NN` пока выдаётся для параллельной сверки с
SUPPLYMAP, но UUID остаётся настоящим идентификатором агрегата. В БД генерация
legacy-номера и номера назначения должна сериализоваться уникальными
ограничениями/sequence, а не локом приложения.

Application layer уже определяет транзакционные сценарии создания и handoff
через Unit of Work. Повтор `creation_key` с теми же данными возвращает исходную
пачку, а с другим payload отклоняется. Повтор handoff читает существующее
outbox-сообщение и не создаёт второй audit/outbox. In-memory реализация
существует только внутри тестов и не подключается к FastAPI.

SQLAlchemy-адаптер и первая Alembic-миграция реализуют эти порты. В эксплуатации
движок включается только через `ERP_DATABASE_URL`; автоматического `create_all`
на старте нет. HTTP write API закрыт серверной auth-зависимостью: имя сотрудника
не принимается из тела запроса, handoff дополнительно требует `buyer/admin`.

### Импорт позиций из расчёта (RQ-5)

(Google Sheets API, см. «Оформить заявку» ниже). `POST /api/requests/import/parse` — запасной путь без Google:
клиент передаёт отображаемые значения листа ЗКП (≤ 20 колонок) и ЗКЗ!B2; `parse_zpk` ищет строку заголовка с
«Обозначение» и «Без НДС», пропускает строки без обозначения, ЕД.ИЗМ предзаполняет по типу (`Кабель`,
`Провод`, `ТУТ`, `Шлейф` → «м», иначе «шт»); проект пустой → из названия файла без «Расчёт».
`POST /api/requests/import` — `importRequests_`: те же гейты в том же порядке и с той же формулировкой

при любом отказе пачка не создаётся. Один дедлайн на пачку, одно назначение `<проект>.NNN` на всю пачку,
АРТИКУЛ КД = Обозначение, КАТЕГОРИЯ по умолчанию «Общепром», затем правило ОП/ИП. Аудит
`request.created` несёт `source: "import"`, идемпотентность та же, что у формы (`Idempotency-Key`).

## Первый контур закупки

`procurement.domain` сам назначает входящей строке статус `Новый` и ревизию
`A`; событие Requests не содержит этих решений. Consumer блокирует очередное
необработанное outbox-сообщение, идемпотентно создаёт строку и в той же
транзакции пишет audit и `published_at`. Отдельный polling-процесс не входит в
HTTP-приложение и может масштабироваться через `FOR UPDATE SKIP LOCKED`.

Взятие в работу разрешено закупщику только из `Новый`. Повтор той же команды
тем же закупщиком ничего не записывает, а захват другим отклоняется. Факты может
редактировать только владелец строки в `В работе`; полный набор готовности
автоматически переводит её в `Готов к запросу`. ORM использует поле `version`,
поэтому конкурентная запись не проходит молча.

Повреждённое integration event не блокирует всю очередь: ошибка фиксируется в
outbox, повтор откладывается с backoff, а после пяти неудач событие переходит в
dead-letter. В лог попадает только UUID сообщения, не его payload.

После заполнения фактов закупщик последовательно фиксирует запрос поставщику,
счёт с ожидаемой датой и оплату. Только переход `В оплату → В пути` публикует
самодостаточное `receiving.expected`; Receiving не читает таблицы Procurement. Обратно, от приёмки к строке
закупки («Карантин», «Готово»), статус несёт таймер `sync_receipt_stages` — см. «Приёмка → строка закупки».

**«Согласование» и «Отменено» вне линейного порядка — решено агентом, проверить (PR-1, 2026-09-28):**

их в любой момент. В ERP это три команды владельца строки: `POST /api/procurement/{id}/approval`,

- Только до оплаты (`В работе` … `В оплату`). После `В пути` строка уже в приёмке, а отмена оплаченного —
  это возврат денег (для недовоза он есть: дозавоз). SUPPLYMAP позволяет и позже, но там это только флаг
  на листе, который синк Ожидания пропускает.
- Выход из «Согласование» возвращает строку на этап, до которого дошли её данные (счёт → `В оплату`,

  статус выставляют руками, а комментарий `Config.gs` описывает возврат «в В работе» — данные строки

- «Отменено» окончательно: из него нет ни «Согласование», ни возврата (так гласит комментарий

### Деньги строки закупки

`procurement.money` — чистый порт `Currency.gs` и `kpApplyCurrencyAndFact_`.

**Поля и пересчёт:**
- Факт-цены: ЦЕНА без НДС, ставка НДС, ЦЕНА С НДС, СУММА.
- Кроме них в строке ВАЛЮТА и реквизиты счёта: НАИМЕНОВАНИЕ (Счет), № и ДАТА СЧЕТА.
- Пересчёт идёт от ведущего поля (`net`/`gross`/`vat`/`qty`/`sum`); без явного поля действует правило КП.
- СУММА = ЦЕНА С НДС × КОЛ-ВО, каждое производное значение округляется до копеек.
- Инвалюта: каждая сумма × курс ЦБ (`Value/Nominal`) × 1,065, после чего ВАЛЮТА становится RUB.
- Числа принимаются так, как написаны в счетах: «1 234,56», «1,234.56».

**Гейт `PUR_PAY_REQUIRED`** (документ по качеству не входит, потому что `ENFORCE_QUALITY_DOC=false`):
- требуемые поля: ВАЛЮТА, обе цены, КОЛ-ВО и ЕД.ИЗМ (факт), СУММА, НАИМЕНОВАНИЕ (Счет), ОЖИД. ДАТА;
- без них счёт не принимается (`Жду счет → В оплату`);
- тот же гейт повторяется на оплате (`В оплату → В пути`). Строки, ушедшие в оплату до денежного блока,
  не оплачиваются, пока закупщик не допишет деньги; править их можно в `Жду счет` и `В оплату`.

**Намеренные отступления от SUPPLYMAP (решено агентом — проверить у бухгалтера):**
- *Дата курса.* SUPPLYMAP берёт курс на сегодня, в момент ввода. ERP берёт:
  - дату оплаты, иначе ДАТУ СЧЕТА, иначе уже сохранённую дату, иначе сегодня (МСК);
  - курс и дату хранит в строке, и повторное сохранение берёт сохранённый курс ЦБ, так что сумма не плывёт;
  - хранит и исходные суммы в валюте счёта (`source_*`), чтобы при оплате один раз пересчитать
    инвалютную строку по курсу дня оплаты.
- *ЦБ не ответил.* Запрос повторяется, как `withRetry_`: 3 попытки, паузы 0,4 и 0,8 с, только сетевые
  ошибки и 5xx. SUPPLYMAP после этого пишет суммы в валюте как есть. ERP вместо этого:
  - отвечает 409 `manual_rate_required`;
  - закупщик вводит курс вручную, и строка сохраняется с пометкой «курс введён вручную»;
  - следующее сохранение при доступном ЦБ заменяет ручной курс курсом ЦБ той же даты, пересчитывает суммы
    и снимает пометку; в audit остаются оба курса;
  - после оплаты деньги закрыты, поэтому для этого есть отдельная команда
    `POST /api/procurement/{id}/exchange-rate/reconcile`.
- *Округление* — Decimal `ROUND_HALF_UP` вместо JS float `Math.round`. Результаты расходятся только на
  float-артефактах вроде 1.005.
- *Отрицательные суммы* отклоняются. В SUPPLYMAP проверки нет.

### Запрос поставщику

`build_supplier_requests` — перенос `buildSupplierRequestsCore_` (`SupplierRequest.gs`), команда

### Форма «Внести КП»

Порт `Kp.gs` и `KpForm.html`: закупщик открывает из строки «Жду счет» все строки своего заказа
(№ ЗАКАЗА `order_number` из запроса поставщику, PR-3 — как `kpOrderRows_`) в статусе «Жду счет» и одной формой пишет КОЛ-ВО и ЕД.ИЗМ (факт), деньги,
ВАЛЮТУ, ОЖИД. ДАТУ, НАИМЕНОВАНИЕ (Счет), № и ДАТУ СЧЕТА. Без счёта статус не меняется. Со ссылкой на счёт
та же команда после записи КП переводит все строки заказа «В оплату». Если гейт `PUR_PAY_REQUIRED` не
пускает, данные КП остаются, ошибка возвращается в форму (`invoiceError`). Файл КП разбирается по шапке
«Наименование | Кол-во | Цена | НДС» в первых 8 строках (`kpExtractItems_`, НДС раньше «цены»), строки
сопоставляются с заказом по НАИМЕНОВАНИЮ (Расчет) и (Сайт): сначала точное нормализованное имя, затем
вхождение в любую сторону (`normName`). API: `GET /api/procurement/kp?reference=`, `POST /kp/parse`, `POST /kp`.

**Решено агентом — проверить (PR-7, 2026-09-28):**
- *Форматы файла.* SUPPLYMAP конвертирует любой файл через Google Drive. ERP читает сам `.xlsx` (первый
  лист, без внешних библиотек) и `.csv` (UTF-8 или cp1251, разделитель `;`, `,` или табуляция), до 5 МБ.
  `.xls`, `.ods` и PDF отклоняются: «Поддерживаются файлы КП .xlsx и .csv». Файл едет в JSON как base64,
  как в `parseKpFile`, и нигде не хранится.
- *Сопоставление на сервере.* В SUPPLYMAP его делает клиент; в ERP `POST /kp/parse` возвращает и позиции,
  и совпадения со строками заказа, чтобы правило жило в одном месте и было покрыто тестами.
- *Одна транзакция на заказ.* Строка другого заказа, чужая строка, не «Жду счет» или устаревшая версия
  откатывают всю запись КП. В SUPPLYMAP строки пишутся по одной.
- *Счёт.* Один файл на заказ («счёт на заказ», `Kp.gs` → `uploadInvoice`), см. «Файл счёта» ниже. Счёт
  принимается для всех строк заказа или ни для одной.
- *Пустое поле очищает значение*, как в `submitKp_`: форма присылает все поля строки. КОЛ-ВО (факт) ≤ 0 и
  ОЖИД. ДАТА раньше создания строки отклоняются (в SUPPLYMAP проверки нет).
- *Курс* выбирается по тем же правилам, что у денег одной строки (дата счёта, иначе сохранённая, иначе
  сегодня), а не на сегодня, как в `kpApplyCurrencyAndFact_`. Если ЦБ молчит, форма просит один ручной курс
  на всю отправку.

### Файл счёта

Порт `Invoices.gs uploadInvoice`. Закупщик выбирает файл в форме счёта строки («Жду счет»), в «Заменить счёт»
или в «Внести КП» (один на заказ). `POST /api/procurement/invoice-files` кладёт файл в таблицу
`procurement_files` (миграция `0067_procurement_invoice_files`) под именем «Счёт № <№> от <дата> <поставщик>
<назначение> <№ заказа>.ext» и возвращает ссылку `/api/procurement/files/{id}` (открывается с правом просмотра
закупки) и распознанные № и дату (`parseInvoiceText_`, `wordDate_`, `numDate_` перенесены один в один).
Транспорт файла (base64 в JSON, ответ inline) общий с УПД отгрузки — `app/shared/stored_files.py`.

**Решено агентом — проверить (2026-09-29):**
- *Распознавание.* SUPPLYMAP гоняет файл через OCR Google Drive. У ERP OCR нет: `app/shared/pdf_text.py` без
  внешних библиотек читает текстовый слой PDF (Flate-потоки, шрифты с ToUnicode, однобайтовые — как cp1251).
  Скан или фото текстового слоя не имеют — форма пишет «Текст из файла не читается (скан или картинка) — № и
  дату счёта впишите вручную», как SUPPLYMAP при сбое OCR.
- *Два шага вместо одного.* SUPPLYMAP в том же вызове пишет ссылку, № и дату в строки. ERP возвращает их в
  форму, закупщик проверяет и отправляет обычной командой (`/invoice`, `/invoice/replace`, `/kp`) — гейт
  `PUR_PAY_REQUIRED` и смена статуса остаются в одном месте. `/invoice` принимает № и дату счёта (пустое не
  трогает сохранённое, как `setIf`). Файл, по которому форму так и не отправили, остаётся в хранилище.
- *Проверки загрузки.* Файл принимается только на свою строку и не на отменённую; до 20 МБ (в SUPPLYMAP
  лимита нет). Пей-гейт проверяется при отправке формы, а не при загрузке: форма КП пишет данные раньше счёта.
- Ссылкой на счёт считается абсолютный http(s)-адрес или путь файла из хранилища закупки.

## Приёмка и склад

Receiving владеет поставкой и входным контролем. Неверный товар и просрочка
терминальны (`Возврат`), отсутствие документов и устранимые несоответствия дают
`Ожидание/Карантин`, а один лишь излишек принимается по фактическому количеству.
ГРН выдаётся в серии назначения `<prefix>.<YY>.<7 digits>`; неизвестное
назначение требует явного выбора только из `CSM/PPM`.

Принятая позиция не попадает на склад до физического адреса. После размещения
Receiving единожды публикует `warehouse.received`. Warehouse агрегирует по
`склад + ГРН + пакет`, считает `баланс = приход − списано` и отдельно хранит
резерв. Списание не может затронуть резерв или уйти ниже нуля; возврат списания
не может превышать ранее списанное количество.

Идентификатор товара в складской партии — `article`; `name` остаётся отдельным
необязательным описанием, а `series` означает партию изготовителя и не заменяет
наш ГРН. Миграция старых данных копирует прежнее `name` в `article`, поэтому
количественная история и ключ партии не меняются.

Ручной складской ввод требует артикул и предлагает наименование, серию и тип из
уже известных партий и версионного снимка БД.Технология. Распознавание корпусов
и кодов коаксиальных разъёмов выполняется в workflow, который связывает Warehouse,
References и чистый каталог корпусов Techcards; домен количественного учёта от них
не зависит. Подстановка заполняет только пустые поля и не заменяет решение кладовщика.
Старая строка без артикула и наименования остаётся доступной по временному UI-ключу
`ГРН/пакет`, поэтому её можно раскрыть и исправить без изменения партии.

Разбор артикула (SK-11; `stock05ArtInfo_`, `Stock05.gs:492-684` на `013a986`, дрейф 39a5a97 и d88150d;
`workflows/warehouse_article.py`). Хвост «@ПОСТАВЩИК …» отрезается до любого опознания («0039012025@MOLEX»);
10-значный артикул с ведущими нулями теряет их все («0039012141» = «39012141»). Порядок: точный контакт БД.ТЕР →
`STOCK05_SERIES_RULES_` (серии без рисунка корпуса: Molex Mini-Fit Jr. 1 ряд, Mini-SPOX, KK 254, MX2.0, Milli-Grid,
Mini-Latch, C-Grid III, Nano-Fit; JST XH и аналоги Connfly DS1069 / A2501, PHD и Scondar, контакты SM/XH, USB-A,
M12, GX16, QS8, Schurter 6136, DC-штекер, кнопка PBS-10B) → семейство корпуса (по артикулу без хвоста, по ключу или
по 9-значному номеру внутри описания; пол из названия семейства «SM (розетка)» идёт в наименование) → главный артикул
серии → БД.КОАКС → коаксиал: код поставщика S/N/T/B/U-1xx/2xx (S-211F) → код разъёма (семейства ISMA→SMA, 2.92mm,
3.5mm; B2/B3 у SMA и прецизионных = RG-405/RG-402) → описание «… male/female» → буква поставщика с полом словами.
Кабели — все RG из текста через «/» (RG8X — не RG-8, RG1.37 — не RG-1), «086» / «0.086» = RG-405.

Физический адрес имеет вид `стеллаж + полка A…Z + номер + необязательная ячейка

(`StockLot.create(location_as_is=True)`, для WH-IMPORT) и ручная правка `PUT /api/stock/batches/{id}/location`
(аудит `warehouse.location_corrected`). Перенос всего места такие партии пропускает, как `placeRemap_`.

### Импорт живых остатков (WH-IMPORT)

CLI `app.modules.warehouse.import_stock` читает выгрузку `whExportRead` (`stock_export.py`, без БД) и заводит

**Решено агентом, проверить (WH-IMPORT, 2026-09-28):**

- Тестовые строки (`SM-TEST`) не исключаются: в ERP их нет.

Порт `Receiving.gs:685-704` (RC-12). `POST /api/receiving/{id}/inspect` с `historical: true` сверяет срок
годности не с сегодняшней датой, а с `document_date` (ДАТА УПД/М-15), без неё — с `arrival_date`
(ФАКТ. ДАТА), без обеих — с сегодня. Без флага даты игнорируются, как `useDocDate = false` в SUPPLYMAP.
Год серии ГРН берётся от реального сегодня (`nextGrn_(pfx, today.getFullYear())`), не от даты УПД.

**Решено агентом — проверить (RC-12, 2026-09-29):**
- Даты УПД и прихода не сохраняются в строке приёмки (нет колонок, нет миграции): они нужны только для
  вердикта. В SUPPLYMAP они живут в листе и попадают в акты — вернуть их вместе с актами ВК (RC-9).
- Форма приёмки показывает флаг «Историческая приёмка» и обязательное поле «Дата УПД/М-15»; запасную
  ФАКТ. ДАТА шлёт только API.

### Дозавоз `-Д`

Порт `Receiving.gs:80-224`.

**Как возникает:**
- Первый ВК строки (из `В пути`) с недовозом `заказ − УПД > 0` в той же транзакции публикует
  `procurement.backorder_requested` с ключом `receiving:{id}:backorder` (у ревизии ВК `-ВN` — `id` исходной
  строки, см. «Новый ВК»).
- Повторный ВК из `Ожидание/Карантин` дозавоз не ставит.
- Procurement создаёт строку `<ID>-Д`: если имя занято — `-Д2`, `-Д3`; дозавоз дозавоза — `<ID>-Д-Д`.
  Признак дозавоза — суффикс `/-Д\d*$/`, как `isBackorderId_`, поэтому миграция не нужна.

**Что попадает в строку `-Д`:**
- копия исходной строки: закупщик, поставщик, цена, НДС, валюта и курс, счёт, `paid_at`;
- количество равно недовозу;
- даты очищены, статус `Согласование`.

**Дальше:**
- Закупщик подтверждает досыл новой ОЖИД. ДАТА → `В пути`. Строка публикует свой `receiving.expected` и
  ждётся приёмкой как обычная поставка, минуя «В оплату»: деньги уже уплачены.
- Отмена (`Отменено`) публикует `requests.reorder_requested`. Requests создаёт новую заявку: тот же
  инициатор и позиция, остаток, новый System ID, ССЫЛКА очищена. Заявка сразу уходит в закупку в `Новый`,
  как строка в SUPPLYMAP.
- В сводке снабжения плана производства строка `-Д` — отдельная позиция.

**Намеренные отступления (решение владельца, 2026-09-28):**
- SUPPLYMAP берёт `parseInt` от недовоза. ERP хранит точный остаток: 2,5 м, а не 2 м.
- SUPPLYMAP копирует СУММУ исходной строки за полное количество. ERP пересчитывает сумму на остаток:
  `ЦЕНА С НДС × недовоз`, до копеек.

### Новый ВК `-ВN`

Порт `Receiving.gs:474-551` («Провести новый ВК»), `POST /api/receiving/{id}/vk-revision`.
- Доступно строке с проведённым ВК (есть вердикт), кроме `Архив ВК`. Исходная строка → `Архив ВК`: акты и
  ГРН остаются историей, повторный ВК и размещение по ней закрыты, на склад она не уходит.
- Ревизия — новая строка `<ID>-ВN` (N = 2, 3, … первый свободный) в `В пути`: контекст заказа (строка закупки,
  склад, позиция, назначение, поставщик, заказанное количество, ед.) и ссылка на УПД; приёмочные поля пусты,
  ГРН выдаётся заново при её ВК, как в SUPPLYMAP. Архивирование и ревизия — одна транзакция, два события аудита.
- На одну строку закупки — одна живая строка приёмки (частичный уникальный индекс без `Архив ВК`).

**Решено агентом — проверить (RC-7, 2026-09-29):**
- Ревизию нельзя открыть, если строка уже передана на склад: иначе та же поставка второй раз ушла бы в
  остаток. В SUPPLYMAP такой проверки нет. Исправление принятого на склад — складская корректировка.
- Ревизия ревизии нумеруется от базового System ID (`<ID>-В3`), а не `<ID>-В2-В2`, как дал бы
  `task.id + '-В' + nn` в SUPPLYMAP.
- Дозавоз ставится один раз на поставку: ключ идемпотентности — по корню цепочки ревизий. Если исходный ВК
  недовоза не нашёл, первый ВК ревизии его ставит. В SUPPLYMAP ревизия `-ВN` не находит строку закупки по
  своему ID и дозавоз не создаёт.
- Серия изготовителя переносится в ревизию (та же физическая поставка); приёмщик может её исправить.
- Возвращённую строку (`Возврат`) тоже можно пересмотреть новым ВК, как в SUPPLYMAP.

### Возврат поставщику

Порт `SupplierReturn.gs`, `GET/POST /api/receiving/supplier-return`, кнопка «Возврат поставщику» на экране
приёмки. Кандидаты — строки `Принято` и остаток их партии `ГРН + ПАКЕТ` на ЦАР/ЖУК (порт только на чтение
`workflows/receiving_stock.py`, склад не импортируется в приёмку).
- Пачка по одной поставке: общие причина (6 литералов SUPPLYMAP), № претензии, комментарий и «что с заказом»;
  на каждую строку своё количество, пусто — КОЛ-ВО ФАКТ. Строка не `Принято` пропускается с пометкой, ничего не
  оформлено — ошибка.
- Строка: РЕШЕНИЕ «Возврат поставщику», основание дописывается в ОПИСАНИЕ НЕСООТВ.; «заказ закрыт» → `Возврат`,
  «ждём замену» → снова `В пути` (аналог `supplierReturnFreePushed_`: приёмка замены снова уходит на склад, со
  своим ключом outbox и своим id прихода в партии).
- Склад: если партия лежит на складе и свободного (без резерва) остатка хватает — в той же транзакции событие
  `warehouse.supplier_return_requested`; склад списывает количество строкой журнала вида «Возврат поставщику»,
  НАЗНАЧЕНИЕ — поставщик. Нет ГРН, партия не разложена, не хватает остатка — только статус приёмки, отчёт
  говорит почему.

**Решено агентом — проверить (RC-6, 2026-09-29):**
- В SUPPLYMAP строка журнала СПИСАНИЕ с основанием «Возврат поставщику: …» проводится тиком как ВОЗВРАТ на
  склад (`writeoffIsReturn_` смотрит на начало основания): у свежей партии (СПИСАНО = 0) проводка падает с
  «возврат больше списанного», у частично списанной — остаток РАСТЁТ. ERP списывает, как задумано в шапке
  `SupplierReturn.gs`; вид строки хранится отдельно от текста основания. Баг SUPPLYMAP стоит поправить там.
- Остаток для возврата — свободный (баланс минус резерв): ERP не списывает в резерв (WH-2). SUPPLYMAP сверял с
  полным БАЛАНСОМ.
- Если между оформлением и проводкой партию успели списать или переместить, событие уходит в dead-letter
  (видно в «Операциях»), статус приёмки уже изменён — как в SUPPLYMAP, где непроведённая строка журнала
  висела с причиной в ПРОВЕДЕНО.
- Частичный возврат при «заказ закрыт» ставит строке `Возврат`, хотя остаток партии на складе остаётся —
  как в SUPPLYMAP.

### Реквизиты УПД, партии и пакеты, акты

- Форма ВК хранит № УПД/М-15, дату УПД (всегда, не только у исторической приёмки), наименование по УПД,
  примечание ВК, дату изготовления, описание несоответствия (`receiveFields_`/`batchFields_`). Из закупки в строку
  приходят № заказа и ожидаемая дата. Одно из двух количеств можно не вводить — берётся другое (RC-1); без обоих — 422.
- «+ партия» (RC-13, `applyWaitlistBatchSplits_`): до первого ВК поставка делится на ≥ 2 партии изготовителя. Исходная
  строка — партия 1 (ЗКП = её количество), остальные — строки `<ID>-ПN` с той же строкой закупки; каждая сразу проходит
  ВК со своими количеством, серией, сроком и получает свой ГРН. Сумма партий меньше заказа — остаток уходит в дозавоз.
- «Разукомплектовать на пакеты» (RC-8, `applyUnpackSplits_`): принятая строка с ГРН до раскладки делится на пакеты с
  общим ГРН; сумма пакетов = КОЛ-ВО ФАКТ (±0,001); пакет 1 — исходная строка, пакеты 2..N — копии `<ID>-ПN` с ПАКЕТ = N.
  Каждый пакет раскладывается и уходит на склад отдельно (ключ партии склада — ГРН + ПАКЕТ).
- Строки партий и пакетов делят `procurement_line_id`, поэтому уникальность «одна живая строка на строку закупки»
  считается только по строкам без `split_of_id`.
- Изготовитель, страна, тип/№/дата документа качества (Лист закупки, Config.gs:269-270) и стандарт (Лист ожидания)
  приходят в строку из `receiving.expected` под теми же ключами и правятся в форме ВК; пустое поле формы оставляет
  значение из заказа. Акт ВК печатает их вместо прочерка. НАИМЕНОВАНИЕ остатка на складе — из наименования по УПД,
  пустое — из заказа (Warehouse.gs:411).
- Акты (RC-9, `DocGen.gs` DOC_TYPES): № `ВК/АН/РК/РИ-ГГГГММДД-NN` (`nextSystemId_`, по дню) и дата хранятся на строке.
  Акт ВК — при первом контроле; АН — когда есть несоответствие продукции (без «Излишка» и документов); РК — недостача
  или недовоз, либо брак/не тот товар при РЕШЕНИИ «Возврат поставщику»; недостающие АН/РК выпускаются при повторном
  ВК. РИ — повторный ВК переводит строку из «Ожидания»/«Карантина» в «Принято». Дата ВК/АН/РК у исторической
  приёмки — дата УПД. Печать — бланк `PrintSheet` (`GET /api/receiving/{id}/acts/{kind}`), поля шаблонов SUPPLYMAP,
  семь пунктов результатов ВК отмечаются по ХАРАКТЕРУ НЕСООТВ. (`icrResultMarks_`).
- Очередь приёмки — общая таблица `DataTable`: поиск по словам, отборы по статусу, группировка по поставщику или
  заказу, свои колонки, выгрузка в Excel, копирование ГРН выбранных строк; форма строки раскрывается кликом.

## Комплектация и выдача

Fulfillment получает состав производственного комплекта идемпотентной командой
и создаёт заявку независимо от текущего остатка. Пустой состав не создаёт
заявку. Каждая строка отдельно хранит исходную потребность, зарезервированное и
выданное количество; при нехватке одной партии остаток потребности остаётся
отдельной незакрытой строкой с тем же `requirement_id`. Снятие партии сливает обратно
все свободные строки (без партии, резерва и выдачи) одного артикула + наименования +
единицы в первую из них — и из разных позиций состава, как `issueMergeFreePlan_` (FF-6).

Партия всегда выбирается человеком. Привязка резервирует складской остаток, а
снятие привязки освобождает его в одной транзакции. Только полностью закрытый
комплект можно перевести в `Готов к выдаче`; выдача одним commit списывает все
зарезервированные партии, пишет по строке журнала СПИСАНИЕ на каждую позицию (SK-13) и меняет статус заявки. Ошибка любой строки откатывает
операцию целиком, поэтому частично выданного комплекта не возникает.

После возврата комплекта каждая выданная строка получает явную раскладку:
`годное + брак возвращён + брак не возвращён + израсходовано = выдано`.
Годное количество сторнирует списание исходной партии и при необходимости
перемещает её на новый адрес. Брак хранится в заявке как факт и не увеличивает
доступный остаток; отдельный контур решений по браку появится вместе с
производственной прослеживаемостью.

### Удаление проекта и его хвосты (2026-10-04, «решено агентом — проверить»)

Удаление проекта (`delete_kitset`, экран «Проекты») сознательно шире SUPPLYMAP `tcKitsetDelete`: кроме карточки, реестра, ТК и строк ГП
без движения, оно сносит хвосты проекта, по которым не было движения, — производственные задания без отмеченной работы (нет короба,
сессии, выработки, брака, «взял/закончил») и не отданные в ЖУК, запросы на комплектацию без выдачи и не собранные (резерв возвращается
партии через `delete_fulfillment`), заявки «Новый», не взятые в закупку. Всё с движением остаётся и перечисляется в ответе с причиной;
каждое удаление пишется в журнал. Проект сверяется точно после нормализации (`normalize_project_number` / `project_from_purpose`),
«719К.2» не задевает «719К.21». Один код — `purge_project_tails` — служит и каскаду, и команде
`python -m app.workflows.purge_project_tails <№…> [--yes]` для проектов, удалённых раньше этого правила (без `--yes` — проверка без
записи; проект с карточкой команда не трогает). Сбой хвостов после удаления карточки не валит ответ, а возвращается в `tails_error`.
Повод — владелец 04.10: «я снёс проекты, а остальное не удалилось».

## Производственные задания

Первый этап production-контура переносит только уже реализованные правила
`ProdTasks.gs`. При запуске задание получает неизменяемый снимок маршрута,
поэтому новая редакция техкарты не меняет ранее выданную работу. Операция может
иметь несколько операторов; подготовка рабочего места учитывается целиком, а
штучное время делится между ними.

Планировщик использует настраиваемую смену цеха: рабочие дни, начало/конец,
перерывы и бюджет эффективных часов; отдельно учитывает праздники, отсутствия и
занятость оператора в других неотменённых заданиях. Матрица компетенций задаёт
допуск, звёзды и коэффициент скорости на код операции; пока на код не заведено ни одной строки
(даже с «нет допуска»), допуск не проверяется и вся бригада идёт по норме (`prodSkillOf_`, PX-3). Автоплан строит цепочку
из снимка ЭТК, перебирает передаточные партии 1/5/10/25/100%, подбирает бригаду до
заданного размера и возвращает неулучшаемые варианты по времени первых изделий
и полного завершения. Уже назначенные операции сохраняются, пока мастер явно
не выбрал пересчёт. Ручное пересечение не блокируется, но возвращается мастеру
как предупреждение.

Статус операции не хранится: он вычисляется по сумме неизменяемой годной
выработки. Отмена меняет только статус задания и сохраняет маршрут, назначения и
план как производственную историю.

`Production Plan` — read model над фактами модулей, а не вторая машина статусов. Этап каждой КБ выводится из
фактов выданной ТК, набранного комплекта, запущенного задания, принятой ГП и отгрузки; этап проекта —
самая отстающая КБ. Заявки и закупка формируют сводку снабжения, задания — охват плана. Ручными остаются
append-only комментарий, блокер/снятие блокера, дедлайн, временное переопределение этапа КБ и результат
проверки ТК. Значение `авто` снимает ручной этап; проверка старше текущей ревизии ТК считается
неактуальной. Данные внешнего реестра проектов, если он есть, приходят как атомарно
заменяемая проекция.

Отметка этапа в журнале с пустой КБ — этап всего проекта без КБ (`ProdPlan.gs:170-220`): «авто» её снимает,
терминальный статус реестра важнее, проект с КБ её не замечает. Для `stage` КБ обязательна, только когда она
указана; `tcReview` всегда требует КБ. Этап каждой КБ несёт факты `tc` (ТК выдана или проект с ручной ТК) и
`kit` (набрано) — `TcKitset.gs:776-790`.

**Пустая матрица компетенций — решено агентом, проверить (PX-3, 2026-09-29):**
- Операция с пустым кодом тоже не проверяется: в SUPPLYMAP `prodSkillsIndex_` отбрасывает строки без кода, так
  что под пустым кодом матрицы не бывает.
- Текст ошибки автоплана дополнен «— заведите компетенции», как в `ProdSchedule.gs:108`.
- Ручное назначение по-прежнему не предупреждает о «нет допуска» (`prodPlan_`): это вне строки PX-3.

**Этап проекта без КБ — решено агентом, проверить (DRIFT-prod, 2026-09-28):**
- «Проект без КБ» в ERP — проект без карточек ТК. У проекта с ручной ТК (714К.) без карточек отметка на уровне
  проекта заменяет старт «ТК готова»; в SUPPLYMAP у 714К. есть КБ набора, и отметку он бы не заметил.
- Состав плана не менялся (реестр ∪ проекты с ТК): случай SUPPLYMAP «без состава, но с журналом» уже входит.
  Исключение «голой строки реестра» не перенесено — это открытая строка PP-1 аудита.
- Блокер проекта отдельным полем этапа не заводился: строка плана уже отдаёт `blocker` по тому же правилу, что
  `planJournal_`.
- Добавлены флаг `stage_manual` и выбор «Этап проекта» (авто + этапы) для проекта без КБ; в SUPPLYMAP такую отметку
  пишет только сверка с листом цеха, экрана для неё нет.
- Сверка с листом цеха «ЗАГРУЗ» (`planShopSync_`, `diagPlanSyncFromSheet`, `PLAN_SHOP_STAGE_`, заведение строк
  реестра с листа) не переносится: это мост к живой таблице Google, листа в ERP нет.

Исполнение хранится отдельными агрегатами. `WorkSession` фиксирует исполнителя,
входы и паузы; `ProductionOutput` добавляется один раз и не редактируется;
`ConsumptionEdge` связывает расход входной коробки с выходной. Как в SUPPLYMAP (`prodWorkStart_` /
`prodWorkSubmit_`): на этапе > 1 оператор при старте вводит номера входных коробок, ничего не резервируется; при
сдаче коробки проверяются ещё раз, а годные + брак берутся из них по порядку ввода. Одна сдача — одна новая коробка
с номером, сразу «Закрыта оператором»; экран показывает номер крупно («Напиши на коробке»). Дальше «Подтверждена» →
«Израсходована». Статус «Открыта» (докладывать в коробку) новые коробки не получают. Возврат мастером требует
причину и сохраняет присвоенный номер. Номер коробки — шесть цифр, дефис и
контрольная цифра Луна, как в SUPPLYMAP; ручной ввод терпит пробелы, длинное тире
и пропущенный дефис. ERP выдаёт `000001`–`099999`, SUPPLYMAP — от `100000`, поэтому
при параллельной работе номера двух систем не пересекаются. То же для брака: ERP выдаёт
`Б-000001`–`Б-099999`, выше — место SUPPLYMAP. Номера коробок и «Б-», выданные ERP по схеме 3/1 до
перехода на Луна, миграция `0045` пересчитывает (тело номера не меняется). Только подтверждённый
остаток предыдущей операции может стать входом следующей, поэтому UI не является
границей контроля.

Возвращённую коробку («Возвращена») оператор исправляет, как `prodWorkFix_` в SUPPLYMAP. Новая
`ProductionOutput` с `correction_of_id` заменяет одну запись выработки этой коробки. Старая запись остаётся, но
выпадает из всех сумм, в том числе из лимита «не больше задания». Количество коробки заменяется:
было − старые годные + новые. Разница `годные + брак` на этапе > 1 добирается из тех же входных коробок по порядку
или возвращается в них с последней. Возврат пишется ребром расхода с отрицательным количеством, а родословная
показывает чистое количество. Израсходованная входная коробка, в которую вернули штуки, снова становится
«Подтверждена». После исправления коробка сразу «Закрыта оператором» и ждёт мастера. «Доложить» (`reopen`)
остаётся отдельным действием: это новая работа в ту же коробку, и она только прибавляет.

**Исправление коробки — решено агентом, проверить (PX-1, 2026-09-28):**
- Заменяется одна запись, как в SUPPLYMAP (решение владельца). Исправлять можно только действующую запись;
  каждую запись заменяют не больше одного раза (уникальный `correction_of_id`). Если в коробке неверны две
  сдачи, мастер возвращает её ещё раз.
- У записи-исправления нет рабочей сессии (`session_id` пуст) и нет своего времени: начало = конец, пауз нет.
- Годные 0 при браке > 0 разрешены, как в SUPPLYMAP: коробка может уйти мастеру с нулём. Запрет «пустую не
  закрыть» относится только к обычному закрытию.
- Лимит задания при исправлении проверяется на любом этапе, как в SUPPLYMAP; обычная сдача — только на первом.
- Первый этап: списание материала (ГРН) исправление не трогает. В SUPPLYMAP вход первого этапа не двигается, а в
  ERP расход материала не связан с числом годных.
- Порядок входных коробок для добора и возврата: по времени создания входной коробки (в ERP у расхода нет своей
  последовательности).
- Брак (рамки задал владелец): запись Б- не меняется и не удаляется. Если брак в исправлении изменился, при новом
  количестве > 0 заводится новая Б- с характером и описанием, как при сдаче. Прежняя Б- получает
  `replaced_by_output_id`, а её количество, статус и решение остаются. По заменённой Б- решение уже не
  принимается, и из очереди мастера она уходит.

Первая операция запускается только для задания, связанного с заявкой
комплектации в статусе «КБ Выдана». Её входы ссылаются на строки выдачи и
сохраняют ГРН, пакет и количество; активная сессия резервирует доступный остаток,
а завершение добавляет неизменяемое ребро `ГРН+пакет → выходная коробка`.

Последняя подтверждённая коробка передаётся в уже заведённую позицию реестра ГП
одной транзакцией: коробка становится израсходованной, количество увеличивает
`FinishedGood.accepted`, а отдельная запись связывает номер коробки с ГРН `ГП`.
Повторная сдача той же коробки блокируется уникальностью источника.

Брак является отдельным агрегатом, а не отрицательным количеством в годной
коробке. `ProductionOutput.defect_quantity` фиксирует факт, а `DefectRecord`
получает собственный номер `Б-...`, характер, описание и ссылку на выработку.
Решение мастера хранится отдельной append-only записью с актом/основанием;
исходные данные оператора после решения не переписываются.

Серийные номера резервируются на всё количество задания в той же транзакции,
что и запуск. При ОТК свободные номера связываются с последней коробкой:
принятые получают статус «Принято ОТК», отклонённые — «Брак». Сдача в ГП
разрешена только после ОТК и переводит принятые номера в «Сдано на ГП» с ГРН.
Решение мастера по отклонённым ОТК изделиям хранится отдельной append-only
записью с уникальной ссылкой на протокол контроля; исходный протокол и серийные
номера не переписываются.
Количество брака ОТК отдельно уменьшает доступный остаток коробки.

Средства измерения — самостоятельный реестр с датами поверки. Контроль хранит
снимок выбранных ID СИ; доменная проверка запрещает выключенное или просроченное
СИ независимо от интерфейса. ОТК выполняет отдельная роль `qc`, не оператор.

Отчёт родословной — read model поверх четырёх источников рёбер: расход выданных
ГРН, переходы между коробками, привязка серийных номеров и приёмка в ГРН ГП.
Поиск сначала находит любой совпавший узел, затем возвращает всю связанную
компоненту в обе стороны. Алгоритм графа остаётся чистым и не зависит от SQL.

## Готовая продукция и отгрузка

Модуль `shipping` владеет двумя связанными агрегатами. `FinishedGood` — складской
регистр одной КБ проекта; `Shipment` — заявка со снимком адресата и строками,
которые ссылаются на регистр. Запись отбора изменяет оба агрегата в одной
транзакции. Поэтому отмена или возврат строки не могут оставить расхождение
между `finished_goods.shipped` и суммой набранного в заявках.

**Возврат набранного на склад ГП — решено агентом, проверить (SH-5, 2026-09-29):**
снятие строки (`unpick`) и отмена заявки возвращают набранное в регистр ГП, как `shipUnpick_` /
`shipCancel_` (`Shipment.gs:787`, `1201-1205`). Прогон SH-5 добавил только тесты и оставил два
отступления ERP от SUPPLYMAP без изменений:
- SUPPLYMAP урезает «ОТГРУЖЕНО» в регистре до нуля (`Math.max(g.shipped - it.shipped, 0)`), а ERP
  отказывает, если возврат больше отобранного (`put_back`). Регистр и заявка пишутся одной
  транзакцией, поэтому расхождения быть не должно. Отказ показывает его, а урезание спрятало бы.
- `shipUnpick_` не проверяет статус. ERP разрешает снять строку только до «Упакована»: после
  упаковки уже выпущены PL/DN. Упакованную заявку можно отменить целиком, и набранное вернётся.
  Отгруженную, закрытую или отменённую заявку не снять и не отменить.

Количество клиента (`requested`) и складской факт (`picked`) не объединяются:
недобор остаётся видимым и может быть набран после следующей сдачи цеха.
Переходы статусов и гейты УПД/трека принадлежат доменной модели, а не React UI.
PL/DN на этом этапе получают только учётные номера; генератор файлов остаётся за
границей модуля до отдельного переноса шаблонов.

**Набор при заведении заявки — решено агентом, проверить (SH-1, 2026-09-29):**
как `shipRequestCreate_` (`Shipment.gs:717-735`), создание заявки менеджером сразу
набирает со склада ГП `min(заказано, остаток)` и присваивает PL/DN → «Упакована»;
флаг `no_docs` («Без отгрузочных документов») останавливает на «Собрана». Если цех
ещё ничего не сдал, заявка остаётся «Новая», кнопка «Набрать» у кладовщика — как
раньше. Решения агента: (1) автонабор выполняется правом менеджера, отдельная
проверка роли склада не нужна — это действие системы, как в SUPPLYMAP; (2) создание,
набор и упаковка — одна транзакция и три записи audit (`created`, `picked`,
`packed`); в SUPPLYMAP сбой автонабора не отменял созданную заявку, здесь сбоя вне
валидации нет, поэтому откат всего целиком безопаснее полусозданной заявки;
(3) «Упакована» ставится по учётным номерам PL/DN — файлов PL/DN пока нет (см. выше).

**Очередь ГП из карточки проекта — решено агентом, проверить (SH-2, 2026-09-29):**
порт `shipQueueForProject_` / `shipGpDropProject_` (`Shipment.gs:577-618`, ADR 0016 §1).
Заведение проекта живёт в легаси ERP, поэтому shipping даёт две идемпотентные команды,
которые зовёт заведение и «Обновить из расчёта»: `POST /api/shipping/project-queue`
(проект, заказчик, КБ с тиражом) и `POST /api/shipping/project-queue/drop` (снос
карточки). Ручная регистрация `POST /api/shipping/goods` остаётся. Решения агента:
(1) КБ без положительного тиража строкой ГП не становится (в ERP «в заказе» > 0) и
возвращается в `skipped`; в SUPPLYMAP встала бы строка с нулём; (2) пустое
наименование заменяется артикулом, затем КБ — наименование в ERP обязательно;
(3) КБ сравнивается без учёта регистра и пробелов, как `shipGpKey_`, а номер проекта —
точно после обрезки пробелов: нормализации `projNoNorm_` в shipping нет, поэтому
вызывающий передаёт канонический номер; (4) строка, уже названная в заявке на
отгрузку, при сносе остаётся, даже без приёмки и отгрузки: на неё ссылается строка
заявки; (5) повторная КБ в одной карточке берётся первой, остальные молча
пропускаются; (6) тираж сравнивается до сотых, как `round2_`.

**Адресат проекта — решено агентом, проверить (SH-3, 2026-09-29):**
порт `ОТГРУЗКА.ПРОЕКТЫ` / `shipAddrEff_` / `shipProjPatch_` (`Shipment.gs:160-170, 318, 564-573`).
Таблица `shipping_project_addressees` — строка на проект: получатель, точка, контакт,
телефон, условия доставки, ТК, тип УПД. Карточка правит её через
`PUT /api/shipping/project-addressee`: присланное поле заменяет, пустое стирает,
неприсланное остаётся. Пустое поле заявки наследует карточку проекта первой позиции
(`shipHeadEff_`), своё непустое сильнее; после создания набранные в заявке точка,
контакт и телефон запоминаются за каждым её проектом, пустое не стирает. Решения
агента: (1) получатель тоже «своё сильнее»: в SUPPLYMAP карточка перебивает получателя
заявки только потому, что упаковка пишет туда заказчика-заглушку, а ERP заглушку не
пишет; без своего и проектного получателем становится заказчик (`shipPackProject_`);
(2) заявка хранит снимок адресата на момент создания: позднейшая правка карточки уже
созданные заявки не меняет (в SUPPLYMAP наследование живое, при чтении); (3) без
точки ни в заявке, ни в карточке заявка отклоняется; условия доставки и тип УПД могут остаться
пустыми, как в SUPPLYMAP (возврат 29.09): пустой тип УПД для гейта «Отгружено» — не ЭДО, нужен файл УПД; (4) проверки
тестовых ID (`isTestId_`) нет — в ERP тестовых проектов в общей базе нет;
(5) экран карточки проекта в React пока не сделан: API готов, форма заявки по-прежнему
присылает все поля.

## Справочники

Модуль `references` не смешивает ручные настройки с нормативной базой
техопераций. Три пользовательские карты заменяются атомарно и защищены
уникальностью нормализованного ключа. Это не позволяет одной ссылке поставщика,
одному изготовителю или одному сечению молча получить два разных значения.
Карта «ГОСТ-сечение → AWG» — цеховой справочник СПР.КАБ из SUPPLYMAP; сборка
техкарты передаёт её в подбор сечения под норму обжима. Поправка обжима
1,0 мм² → 18 AWG зашита в коде и сильнее карты, как в SUPPLYMAP.
Миграции 0025 и 0043 засевают карту всеми строками таблицы AWG листа СПР.КАБ с
числовым ГОСТ и целым AWG (19 строк, как `gostAwgMap_`); строки админа сильнее сида.

База `ОП/ОБ/ТЕР/КОАКС` импортируется только полным снимком с `schema_version`,
датой исходника и датой импорта. Поиск читает этот снимок, но не меняет его.
Так смена структуры источника становится явной миграцией, а редактор небольших
карт не превращается в интерфейс ручного исправления тысяч нормативных строк.

Станок по размеру кабеля (SUPPLYMAP bfef60d/061f3b5, пин `references` → d2df8b8)
«решено агентом — проверить»: в SUPPLYMAP это данные, а не алгоритм — у одной
операции две строки «Оборудование» в БД.ОП-ОБ и шаблоне ТК (CUT_COAX — BZW-886+Q2
«кабель Ø до 5,5 мм» и BZW-50X «свыше»; STRIP_WIRE — EW-1090 и BZW-D2.0S(R);
PRS_ТМЛ — YQK-70 и BZW-20TS; CUT_NEYLON — только BZW-200+H), станок выбирает
оператор по паспорту кабеля; кода, который выбирает станок по диаметру, в
SUPPLYMAP нет. Поэтому в ERP не вводится правило автоподбора станка. Снимок
БД.Технология v14 несёт у ОБ только «Для базы» и тип, у ОП — время; связь ОП-ОБ,
цены станков и «Уд.Цена МШ» в снимок не входят — строки ОБ.093–ОБ.104 и групповые
«(R)» (ОБ.099.X, ОБ.100.X) приходят со следующим импортом снимка как есть. Два
станка в операции видит техкарта (оборудование шаблона — зона `techcards`).

Шаблоны ТК и второй станок (DRIFT-tc-bfef60d → TC-TSV-IMPORT, «решено агентом — проверить»):
библиотека шаблонов теперь строится `npm run sync:techcard-library` из **зеркала БД.ТК**
`_local/db/БД.ТК/*.tsv` на SUPPLYMAP `main` (то, с чем db.mjs pull/push синхронизирует живой
лист; фикстура `tc-library.json` отстала — её последний коммит b0d45b9, а bfef60d правил только
зеркало). 118 шаблонов вместо 115. Разбор TSV — как у db.mjs (`fromTsv`): строка файла = строка
шаблона, ячейки через TAB, в ячейке обратный слэш, TAB и перевод строки экранированы, хвостовые
пустые ячейки обрезаны, 1-я строка — заголовок = `title`. Формат `techcard-library.json` не менялся
(`id`, `title`, `category`, `rows`; плюс `images` из `_images.json` зеркала — бэкенд его уже
читает; сейчас картинка одна, `sdr-coax-housing-пайка-экрана-a`). Отличия от фикстуры: (1)
`category` в TSV нет — берётся из фикстуры для 115 общих id, для 3 новых выводится из заголовка

  единственный источник, правки портала (`portalRefSave` → `dbMirrorWrite`) сохраняются и обновление зеркала их не
  стирает; ERP ведёт себя так же. Запись справочника хранит `mirror_key` (хеш вкладки/отображаемого текста/`sort_key`
  строки зеркала + номер среди двойников; не меняется при правке) и `edited_in_erp` (ставят `PATCH` и `POST

  остальные записи заменяются как раньше. Отчёт: «пропущено (правлено в ERP)» по вкладкам и всего, то же число — в

  переименовали в самом зеркале, её ключ меняется и появится новая запись рядом. `PUT /supplymap-snapshot` (GAS-выгрузка)
  по-прежнему заменяет вкладки целиком. Записи, созданные до миграции, ключа не имеют и заменяются как обычно.

  «ИЗМЕНЕНО/КЕМ» пусты — ручных правок, которые потерялись бы, нет. Если в SUPPLYMAP появятся правки записей
  через портал (непустое «ИЗМЕНЕНО»), эти листы станут первичными и их придётся импортировать.

## Аудит, задания и уведомления

`audit_events` — append-only доказательный журнал. В отличие от защищённого
Google-листа ему не нужен промежуточный буфер: событие пишется тем же commit,
что и изменение агрегата, а API предоставляет только чтение. Управленческий
экран фильтрует журнал, но не имеет команд изменения или удаления.

Фоновая работа строится на transactional outbox, отдельных идемпотентных
consumer-функциях и dead-letter после исчерпания повторов. `OwnerTick` не
переносится: его синхронизации между листами исчезли вместе с дублированием
данных, а один долгий минутный конвейер снова создал бы голодание хвоста.
Уведомление сначала становится outbox-событием, затем отдельной транзакцией
попадает в персональную ленту; ошибка доставки не отменяет исходную операцию.

### Продюсеры уведомлений (OP-1)

Модуль публикует `notification.requested` через `app/shared/notifications.py` и адресует **id пользователя**
и/или **ключ роли Identity**, а не почту и не имя. Operations при доставке превращает их в почты активных
пользователей (`SqlAlchemyRecipientDirectory`); неактивный, удалённый или ненайденный адресат молча
пропускается (как `if (!list.length) return` в `notifyDispatch_`), событие без адресатов вообще — poison.

| Правило SUPPLYMAP | Где в ERP | Кому |
|---|---|---|
| Блокирующее несоответствие ВК (`Receiving.gs:757-788`) | `inspect_receiving`: статус ≠ «Принято» и есть характер | брак → роль `admin`, прочее → `buyer`, смесь → оба |
| Авто-Карантин по таймеру (`OwnerTick.gs:573-581`) | `quarantine_overdue_waiting` | те же роли |
| Смена статуса Закупки (`OwnerTick.gs:872-903`, `NOTIFY_PURCHASE_STATUSES`) | `notify_initiators` в `run_timers` | `procurement_lines.initiator_id` |
| Комплект готов к выдаче (`Issue.gs:459-474`) | `mark_ready` | `fulfillment_requests.requester_id` |
| Трек-номер отправки (`Shipment.gs:840-850`) | `update_documents`, трек изменился и не пуст | `shipments.manager_id`, нет — все `pm` |
| УПД приложена (`Shipment.gs:888`) | `update_documents`, ссылка на УПД изменилась и не пуста | роль `receiver` |

**Решено агентом — проверить (OP-1, 2026-09-29; пункт «Технолог» — подтверждено владельцем 2026-10-04):**
- «Технолог» = роль `admin`, не `engineer` (подтверждено владельцем 2026-10-04). Задание предлагало `engineer`, но в SUPPLYMAP `PORTAL_ROLE_LABELS_`
  подписывает «Технолог» именно `admin` (`engineer` — «Инженер»), и адресат `QUAR_TECH_EMAILS` в `STAFF_BY_EMAIL`
  имеет роль `admin`. «Снабжение» = `buyer`. Поменять — одна константа `TECHNOLOGIST_ROLE`.
- Уведомление о статусе Закупки — опрос состояния, как в SUPPLYMAP, а не хук в каждой команде: так его видят
  все пути смены статуса (действия закупщика, синхронизация с приёмкой, отмена). Анти-дубль —
  `procurement_lines.notified_status` (аналог `notified_<id>`), ставится и когда адресата нет.
  Миграция взводит его текущим статусом, чтобы релиз не разослал уведомления по всем открытым строкам.
- Несоответствия ВК — одно уведомление на строку, SUPPLYMAP собирал одно письмо на прогон листа.
- Трек без найденного менеджера уходит всем `pm` — это правило `shipTrackRecipients_`, а не молчание.

## Identity

`identity_users.id` — единственный ключ владения и аудита; ФИО остаётся только
снимком для отображения. Идемпотентность создания заявки ограничена UUID
инициатора, поэтому одинаковые браузерные ключи разных сотрудников не
конфликтуют. Доступ вычисляется как роль плюс персональное перекрытие
`none/view/edit`, причём write API требует именно `edit`, а не просто роль.

Хэш SUPPLYMAP `SHA-256(email:PIN)` и токен в `localStorage` не воспроизводятся: PIN и пароль хранятся
Argon2id с параметрами OWASP, сессия — случайный непрозрачный session token в HttpOnly-cookie, отдельный CSRF secret,
лимиты попыток (ID-4, `Portal.gs:252-306`: 10 неудач на учётку и 30 по всем учёткам за 10 минут,
плюс потолок ERP 300 на адрес клиента; каждая неудача — `identity.login_failed` с номером попытки, на пороге —
уведомление роли admin в ленту вместо письма владельцу), скользящий и абсолютный срок
сессии. На каждом запросе активность сотрудника и актуальная матрица прав
читаются заново; деактивация отзывает все сессии.

Вход по PIN (SUPPLYMAP Portal.gs `portalStaffLite_` / `portalLogin` / `portalRevealPin_`, `PORTAL_PIN_RE_`):
экран входа — «Кто ты» (поиск по имени в списке активных сотрудников: `GET /api/auth/login-staff` без входа,
только id, ФИО, отдел — почт нет) + «PIN-код»; `POST /api/auth/pin-login {who, pin}`. `who` — id из списка либо
почта/логин (запасной путь). Неизвестный или отключённый сотрудник и неверный PIN дают один ответ «Неверный
сотрудник или PIN.» (401) и идут в те же счётчики ID-4, что и вход по паролю (ключ учётки — `login:<логин>`,
общий с паролем; 30 на всех; потолок клиента), с `identity.login_failed` (`method: pin`). «PIN ещё не назначен —
обратись к администратору.» (422) — не неудача. PIN — 6–8 ASCII-цифр. Успешный вход — `identity.login_succeeded`
(`method: pin`) и отметка «входил» (`identity_users.seen_at`, как `portal_seen_*`).
Пустой PIN — «узнать PIN» (онбординг `portalRevealPin_`): только при включённом режиме (`identity_settings.pin_reveal`,
владелец включает `python -m app.identity_admin pin-reveal on|off` — аналог `pinRevealOn/Off`, по умолчанию выкл.),
только тому, кто ни разу не входил, и никогда роли admin. Хранимый PIN — хэш, поэтому «показать» = выдать новый
(6 цифр, первая не 0), сохранить хэш и показать один раз (`{reveal, name, pin}`, сессии нет); экран просит
записать и подставляет PIN в поле. Каждая выдача — `identity.pin_revealed`. Отказы — тексты SUPPLYMAP: «Введи PIN.»
(режим выкл./админ) и «Введи PIN. Пароль ты уже получал — если забыл, обратись к администратору.» (422, не
неудача). Проверку неизвестного сотрудника пустой PIN не обходит. Миграция 0062 (`pin_hash`, `seen_at`,
`admin_mode_until`, `identity_settings`) отмечает «входил» всех, у кого в журнале есть `identity.login_succeeded`.
Вход по логину и паролю остаётся рядом («Войти по логину и паролю»): у существующих учёток PIN нет, пока его не
назначит админ.

«Режим админа» (Portal.gs `portalCanAdminMode_` / `portalAdminMode_` / `portalToggleAdmin`): только учётке
`GOD_MODE_EMAIL` (`tektra.real.tektra@gmail.com`, Config.gs; в ERP — `ADMIN_MODE_EMAIL` в `identity/domain.py`).
`POST /api/auth/admin-mode {on}` ставит/снимает флаг текущей сессии (`identity_sessions.admin_mode_until` = сейчас +
6 ч — TTL кэша SUPPLYMAP; другая сессия того же человека не затронута). Пока флаг жив, эффективная роль — admin:
права = строка admin матрицы «Доступов» + персональные исключения человека (`portalAccessFor_('admin', email)`),
открываются «Сотрудники» и «Доступы» (`portalRealAdmin_` учитывает режим); роль в справочнике не меняется и в
правило «остаётся админ» не входит. Остальным — 403 «Режим админа недоступен для этого аккаунта.». Аудит —
