## Номер и неизменяемая идентичность

Формат: `<category>.<YY>.<NNNNNN>`, например `PPM.26.000002`, `R&D.26.000001`.
Категории: `PPM`, `PAM`, `GOS`, `SUB`, `CSM`, `FRX`, `R&D`; `R&D` не заменяется на RND.
Каждая категория имеет независимый счётчик на полный календарный год. Начало — 1, предел — 999999.
Год определяется **серверным временем регистрации в Europe/Moscow**, которое передаётся с часовым поясом.
Дата УПД, ВК или изготовления не определяет год номера. Повтор через Новый год возвращает первоначальный номер.
Один ГРН допускает несколько пакетов/складских представлений; `UNIQUE(grn)` на `warehouse_lots` запрещён.
Категория относится к конкретному приходу/акту, каталог артикулов не дублируется.

## Порт, DTO и транзакция

Чистые `frozen=True` DTO: `backend/app/modules/warehouse/grn.py`.
Межмодульный импорт для C/D: `app.workflows.grn_allocation` — реэкспорт DTO/ошибок и фабрика порта.
Домены receiving/shipping не импортируют ORM склада или этот workflow; их application получает внедрённый порт.

```python
from app.workflows.grn_allocation import GrnCategory, GrnContext, GrnRequest, fingerprint_body, grn_allocator

# В уже открытой транзакции caller_session; создание другого UoW запрещено.
identity = grn_allocator(caller_session).allocate(
    GrnRequest(
        category=GrnCategory.PPM,
        source_kind="warehouse_receipt",
        source_op_id=str(acceptance_id),
        context=GrnContext(),
        body_fingerprint=fingerprint_body(normalized_acceptance_payload),
    ),
    registered_at=server_now,
)
# Тот же caller_session пишет приход, остаток, audit/outbox и задание печати.
# Commit/rollback принадлежит вызывающему UoW.
```

`GrnAllocationPort.allocate(request, *, registered_at)` возвращает `GrnIdentity`:
`id: UUID`, `number: str`, `category: GrnCategory`, `full_year: int`, `serial: int`,
`registered_at: aware datetime` (UTC), `source_kind: str`, `source_op_id: str`, `context: GrnContext`.
`allocate_many(tuple[GrnRequest, ...], *, registered_at)` возвращает tuple в исходном порядке;
блокирует счётчики в порядке категорий, откатывает весь набор при конфликте. Использовать для смешанных партий,
не вызывать несколько независимых аллокаторов в произвольном порядке внутри конкурентных пакетных команд.

Порт требует `session.in_transaction()`. Сам `__enter__` существующего UoW создаёт Session лениво:
до вызова номера транзакция должна начаться через обычное чтение/запись либо явный `session.begin()`.
Аллокатор не вызывает commit и не создаёт сессию. PostgreSQL использует атомарный
`INSERT ... ON CONFLICT ... DO UPDATE ... WHERE last_serial < 999999 RETURNING`, включая первый номер.
SQLite использует тот же принцип; при ещё не начатом DBAPI-транзакционном блоке выполняется `BEGIN IMMEDIATE`,
чтобы RELEASE SAVEPOINT не зафиксировал номер раньше прихода. Ошибки сериализации/блокировок повторяет
обвязка **всего** UoW; аллокатор не повторяет отдельно движение остатков.

| Поток | source_kind | source_op_id |
| --- | --- | --- |
| Ручной/сканированный приход | `warehouse_receipt` | Существующий `acceptance_id` строки |
| Быстрое внесение | `warehouse_quick` | Стабильный UUID команды, повторяется при retry |
| ВК: одиночный/пакетный/поставка | `receiving` | UUID физического приёмочного события; все три API используют один ключ |
| Приёмка ГП | `finished_goods_act` | UUID акта/движения приёмки, созданный до номера |

Ключ уникален в паре `(source_kind, source_op_id)`; длины 32/128, внешние пробелы запрещены.
`legacy` зарезервирован миграцией. Разукомплектование и outbox-проводка используют уже выданный `grn_id`,
новый номер при доставке события не получают. Новая физическая приёмка/акт требует другого ключа.
Первая строка aggregate `finished_goods` и первый акт ссылаются на одну идентичность; последующие акты — на свои.

`body_fingerprint` — SHA-256 полного нормализованного содержания команды: артикул, количество, единица,
пакет, приход, паспорт и другие существенные поля. `fingerprint_body(dict)` принимает только JSON-значения;
Decimal передаётся нормализованной строкой, UUID/даты — строками. Исключить время попытки, transient version
и прочие поля транспорта. Category/context автоматически входят в итоговый хеш дополнительно.
Одинаковый ключ/содержание возвращает прежний DTO без расхода номера; изменение содержания, категории
или контекста вызывает `GrnConflict` (API: 409). `GrnCapacityExceeded` — явная ошибка исчерпания, без переноса
в седьмой разряд. Ошибки валидации DTO — `ValueError` (API: 422). Не переводить конфликт в успех с новым номером.

## Контекст категории

`GrnContext` хранит `owner_id: UUID | None`; остальные поля — `str | None`, непустые, до 512 знаков.
Имена JSON совпадают с именами полей. `context.payload()` преобразует UUID в строку; неизвестное — `null`.

| Категория | Обязательные поля | Значение |
| --- | --- | --- |
| PPM | Нет обязательного дополнительного поля | Заказ/проект указывается при наличии |
| PAM | `purpose` или `equipment` | Работа, оборудование, оснастка |
| GOS | `purpose` | Эксплуатационная цель/подразделение |
| SUB | `subcontractor`, `production_order`, `acceptance_document` | Подрядчик, производственный заказ, основание приёмки |
| CSM | `owner_id`, `customer_order`, `transfer_document` | Владелец, заказ клиента, документ передачи |
| FRX | `production_order`, `acceptance_document` | Производственный заказ и акт сдачи |
| R&D | `project`, `purpose` | Проект опытной разработки и назначение |

`project` — существующий ключ проекта; `customer_order`/`production_order` — стабильные ключи заказов.
Их существование, права и совместимость проверяют B/C через порты соответствующих модулей: это не свободные
названия для обхода привязок. `equipment` — назначение/обозначение оборудования, UUID-модель не придумывается.
`owner_id` разрешён только для CSM, FK ведёт в `warehouse_material_owners`.
Регистр владельцев: `id UUID PK`, `display_name VARCHAR(512) NOT NULL`, `legal_identity VARCHAR(512) NOT NULL UNIQUE`;
обе строки непустые. B нормализует юридический ключ (например, `ИНН:...`) и проверяет его до создания.
Заказчик текстом в production-проекте не заменяет этого UUID. Существующие владельцы не угадываются.

## Схема 0218

`warehouse_grn_registry`: UUID PK, `number VARCHAR(32) UNIQUE`, category/full_year/serial,
`is_legacy BOOLEAN NOT NULL`, source_kind/source_op_id, request_fingerprint, registered_at и все поля GrnContext.
`UNIQUE(category, full_year, serial)`, `UNIQUE(source_kind, source_op_id)`; дополнительные составные UNIQUE
обеспечивают FK из физических записей на точные `(id, category, number)` и `(id, owner_id)`.
CHECK ограничивают категории, год 2000–9999, serial 1–999999, канонический номер и обязательный контекст новых записей.
UPDATE/DELETE идентичности запрещены триггером. Исправление — отдельное аудируемое аннулирование/замена;
в этом срезе такая команда ещё не реализуется.

`warehouse_grn_counters`: PK `(category, full_year)`, `last_serial INTEGER NOT NULL CHECK 0..999999`.
Значение — последний занятый номер, следующий = +1.

В **warehouse_lots, receiving_lines, finished_goods_acts, finished_goods** добавлены:

| Колонка | Тип | Назначение |
| --- | --- | --- |
| `grn_id` | UUID, FK + индекс | Общая идентичность |
| `grn_category` | VARCHAR(3) | Снимок категории |
| `grn_context` | JSON | Снимок GrnContext; до выдачи номера — введённый контекст |
| `grn_contract_version` | INTEGER NULL либо 1 | NULL — историческая запись, 1 — новый контракт |
| `material_owner_id` | UUID, FK | Владелец CSM, совпадает с владельцем идентичности |
| `quality_state` | VARCHAR(16) | IQH / QTN / RELEASED / REJECTED / NOT_REQUIRED |
| `quality_basis` | TEXT | Основание решения/освобождения от ВК |
| `quality_decided_by` | UUID | Стабильный ID принявшего решение |
| `quality_decided_at` | DATETIME с timezone | Время решения |
| `quality_version` | INTEGER >= 1 либо NULL | CAS решения о качестве |
| `expiry_required` | BOOLEAN либо NULL | Нужен ли реальный срок годности для этой позиции |

Все новые колонки допускают NULL для истории. Для `grn_contract_version=1` CHECK требует category/context,
quality_state/version, expiry_required и идентичность. Исключение: receiving до номера допускает `grn/grn_id=NULL`.
Для нового CSM обязателен владелец; для других категорий он отсутствует. RELEASED/REJECTED/NOT_REQUIRED требуют
основание, автора и время. PPM/CSM/SUB не допускают NOT_REQUIRED.
Приложение всегда ставит `grn_contract_version=1` для нового прихода; пропуск маркера — только импорт истории,
не пользовательская опция. CHECK не заменяет серверную авторизацию ОТК/guard выдачи и проверки expiry.
GOS/PAM: «ВК не требуется» с основанием; FRX/R&D получают явное решение по своей производственной процедуре.
Частичное освобождение пакета запрещено; отсутствие УПД само по себе не блокирует. Истории «Годен» не присваивается.

У склада ORM-колонки уже объявлены. `_row/_domain` пока сохраняют прежний доменный контракт: обновление старой
партии сохраняет новую метадату. **B возвращает A согласованное расширение этих двух преобразователей** после
добавления полей в StockLot; без этого переключать складские команды нельзя. C добавляет свои ORM-поля и
преобразования в receiving/shipping. Схему повторно создавать не надо.

## Шаблоны и печать: D/E

`warehouse_label_templates.category VARCHAR(3) NOT NULL DEFAULT ''`:
`''` — исторический общий шаблон и не-ГРН виды, остальные значения — семь категорий.
Теперь UNIQUE `(kind, category, format)`; instrument разрешает только `category=''`.
`form_id VARCHAR(128)`, `form_revision VARCHAR(64)`, `form_effective_date DATE`: все NULL либо все заполнены.
Это утверждённая форма, отдельно от существующего integer `version` оптимистической блокировки шаблона.
Не переносить «Форма 05.11 Rev.3» с образца без утверждения. Старые JSON, версии и авторы сохранены буквально.
D обновляет все load/save/reset/select запросы: каждый запрос обязательно включает category, иначе при новых
шаблонах прежний запрос kind+format станет неоднозначным.

`warehouse_label_jobs` получает `grn_id` (FK), `grn_category`, `grn_number`, `grn_provenance JSON`,
`template_kind VARCHAR(16)`, `template_format VARCHAR(8)`, `template_version VARCHAR(64)`,
`form_id/form_revision/form_effective_date` тех же типов. NULL — старая очередь.
Для задания с grn_id обязательны номер, provenance и kind/format/version шаблона.
`template_version`: `db:<целая версия>` либо `builtin:<версия дизайна>`.
`grn_provenance` фиксирует source_kind/source_op_id, context, package, качество, expiry и полный label payload,
использованный рендерером. Бинарный результат уже хранится в tspl/png; новая очередь его не пересчитывает.
Триггер запрещает менять payload, происхождение и форму задания с grn_id; claim/lease/status/result продолжают работать.
Повторная печать создаёт новое задание. D добавляет ORM-колонки в своих файлах и заполняет снимок атомарно с печатью.

E: настройка шаблонов живёт в карточке TSC MB341 в «Оборудовании»; отдельный пункт дизайнера не вводится,
старый маршрут перенаправляется в карточку. Формат полного ярлыка 100×50, TSC монохромный: слово/символ статуса.
Существующие компактные размеры сохраняются. Barcode/QR = точный GRN + существующий суффикс пакета;
leading zeros, `&`, старые шесть/семь цифр сохраняются. E следует окончательным API B/C/D, не вводит свой аллокатор.

## Миграция, история и передача координатору

`0218_grn_registry.down_revision = 0216_equipment_screen_group` **временно**.
0217 занята PR реестра СИ; координатор переподключает 0218 к её фактическому revision id при интеграции
и повторяет тест единственной головы. Не угадывать имя 0217 и не менять уже вошедшую в main миграцию.

До DDL проводится сверка warehouse/receiving/aggregate ГП/актов. Старые распознанные префиксы получают category,
остальные (OLD, ГП, неизвестные/неправильные строки) сохраняются с category=NULL.
UUID исторической идентичности детерминирован происхождением и исходным номером: репетиция up/down/up
восстанавливает те же идентификаторы и ссылки.
Все исторические идентичности имеют is_legacy=true, serial=NULL: шесть/семь цифр не становятся алиасами
и не конфликтуют по числовой тройке. Полный год исторического YY интерпретируется как **2000+YY**;
применимость этой интерпретации проверяется на производственной копии до выпуска.
Счётчики берут максимум числового хвоста обеих длин по каждой категории/году. OLD/ГП не расходуют их диапазоны.
Максимум >999999, оборванные ссылки, конфликт происхождения или повтор raw GRN без доказанной связи останавливают
миграцию до DDL. Миграция не исправляет и не переименовывает такие данные.

Доказательства общей идентичности: явное `receiving:<id>:package:<N>`, существующие receipt/outbox-токены,
валидные ключи одной импортированной позиции при её перемещении, ссылка первого акта на aggregate ГП.
Общий заголовок поставки, артикул, закупочная строка, batch split или supplier replacement revision недостаточны.
Строка склада с несколькими независимыми приёмками не объединяет их в одну идентичность автоматически.
Объёмы, резерв, пакеты, движения, accepted/packed(shipped)/sent, manufacturer batch и байты старой печати не меняются.

Downgrade допускается только до новых данных: при наличии новой идентичности, владельца, шаблона/метадаты печати
или качества он прекращается до изменений. После переключения — отдельное решение восстановления и forward fix.
Координатор выполняет backup → изолированную PostgreSQL-копию production → upgrade → сверку всех таблиц,
GRN/owner/QC, outbox/retry, количеств и shipping-счётчиков. Локальные SQLite-тесты не заменяют эту репетицию.
PostgreSQL-тесты аллокатора включаются только через `ERP_TEST_POSTGRES_URL` на loopback/БД `erp_stock_test`;
без неё они явно skipped, конкурентная модель исполняется на SQLite.

Перед выпуском B/C/D должны завершить ORM/DTO и все точки входа, серверные holds, owner-совместимость,
пропускную способность принтера/сканера, E — интерфейсы. Координатор затем выполняет независимый review,
единый `npm run check`, CI точного коммита и производственную репетицию. A не выполняет commit/push/merge/deploy.
