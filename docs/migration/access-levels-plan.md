# Уровни доступа вместо ролей-должностей (владелец 04.10.2026)

Спецификация владельца: «Права разграничения настраиваются в отдельных параметрах системы администратором».
Уровни: Суперадминистратор (ГД, Учредители) · Администратор (менеджер высшего звена, отвечающий за систему, Дирекция) ·
Коммерческое руководство (Маркетинг, Продажи) · Технический руководитель (Нач. производства, Главный технолог,
Закупщик) · Бригадир (Бригадир, Кладовщик) · Оператор (конечный исполнитель). Должность — отдельное поле `job_title`.

## Модель
- `identity_users.access_level`: superadmin · admin · commercial · tech_lead · foreman · operator (подписи как выше).
- Всегда полный доступ: superadmin и admin; только они видят «Доступы», «Сотрудники» и админ-инструменты; уровни
  superadmin/admin выдаёт и снимает только суперадминистратор; должен остаться хотя бы один активный.
- Остальные уровни — только матрица (админ правит). Списки ролей на маршрутах (`shared/http_auth.py`) убираются —
  решает режим раздела. Новые разделы матрицы: `myops` «Задания» (из `production`), `quality` «ОТК»,
  `shipping_goods` «Отгрузка — склад».
- Флаги человека в карточке: `shop_worker` «Монтажник (работает в цеху)» — заменяет `role == "staff"` в
  `Operator.installer` и карточке; `site_master` «Мастер площадки» — подчинённые в карточке.
- Уведомления — аудитории по разделам: снабжение → `procurement` edit, менеджер проекта → `shipping` edit,
  кладовщик → `shipping_goods` edit; технолог/владелец/безопасность → superadmin+admin; старые ключи в outbox
  разрешаются в те же аудитории.
- Матрица по умолчанию: commercial — проекты, отгрузка, закупка, склад, производство просмотр, заявки правка;
  tech_lead — проекты, техкарты, шаблоны, генератор, справочник, производство, закупка, заявки, комплектация правка;
  приёмка, склад, выдача, ОТК, отгрузка просмотр; foreman — производство, задания, приёмка, склад, комплектация,
  выдача, отгрузка-склад правка; закупка, ОТК просмотр; operator — оформить заявку, мои заявки, задания правка;
  приёмка, склад, справочник просмотр.

## Перенос данных
- Роль → уровень: management→superadmin · admin→admin · prodhead, buyer, engineer→tech_lead · pm, estimator→commercial ·
  master, receiver, qc→foreman · staff→operator. Пустая должность ← русское имя старой роли. `shop_worker` = нынешнее
  правило монтажника, `site_master` = старая роль master. `legacy_role` хранится один выпуск.
- Строка уровня в матрице = ПЕРЕСЕЧЕНИЕ того, что реально могли его члены; каждому человеку — компенсирующие личные
  исключения, чтобы доступ остался ровно прежним. Спящие исключения бывших «всегда полных» ролей — в аудит, не
  включаются. Перед применением — CLI-отчёт «было/стало» по каждому человеку × каждому шлюзу, по получателям
  уведомлений и списку админов (только чтение рабочей базы).

## Партии
1. T1 (opus, миграция 0086 после 0085): схема, перенос, отчёт. Готово, когда фикстура со всеми 11 старыми ролями не
   меняет ни одного шлюза ни для кого; админ остаётся; должность заполнена; повторный прогон ничего не меняет.
2. T2 (opus) шлюзы бэкенда на уровнях и матрице · T3 (opus) флаги монтажника и мастера · T4 (sonnet) аудитории
   уведомлений.
3. T5 (sonnet) фронтенд: только права, без списков ролей.
4. T6 (sonnet) «Доступы» по уровням, флаги и «Должность» в «Сотрудниках»; erp-screens.

Решено агентом — проверить: соответствие ролей уровням (старый admin = «Технолог» → Администратор, ОТК → Бригадир);
superadmin/admin фиксированно полные, у остальных «всегда полный» становится обычной матрицей; пересечение +
компенсирующие исключения; новые разделы и два флага; уведомления по разделам.
Риск: бывшие «всегда полные» (нач. производства) получат правку закупки/отгрузки через исключения и станут получать
уведомления снабжения/менеджера — отчёт покажет это до применения.
