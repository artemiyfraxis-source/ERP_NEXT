# Корпус сборок: чертёж → черновик → правка мастера → образец

Для людей и для агентов. Здесь копятся пары «что набросал черновик» и «что оставил мастер». Каждая пара — образец,
по которому следующие черновики становятся точнее.

## Поток

1. **Чертёж.** Владелец присылает чертёж изделия (жгут, кабель, коаксиал…).
2. **Черновик.** Claude (позже — серверный агент) читает чертёж, записывает, что он говорит, в `spec.md` и набрасывает
   сборку: блоки полуфабрикатов, операции из библиотеки или свои, нормы времени. Результат — «Ручная сборка»,
   `build_config` режима `manual` (`draft.json`). Формат: [`build-config.schema.json`](build-config.schema.json);
   какие карточки есть и какие параметры им нужны — [`vocabulary.md`](vocabulary.md).
3. **Правка мастера.** Владелец (технолог) исправляет черновик в ERP — состав операций, порядок, блоки, нормы, ход
   своих операций. Итог — `final.json`.
4. **Образец.** Разница между `draft.json` и `final.json` объясняется в `lesson.md`: что поправили, почему, и какое
   общее правило из этого следует. Папка с четырьмя файлами — один образец корпуса.

Черновик обязан проходить схему и собираться (`build_etk` в режиме `manual`); правка мастера — тоже. Образец, в котором
`final.json` не проходит схему, в корпус не попадает.

## Устройство образца

```
docs/assembly-corpus/
  README.md  build-config.schema.json  vocabulary.md
  <drawing-id>/
    spec.md       что говорит чертёж
    draft.json    build_config черновика (как его выдал агент, без правок)
    final.json    build_config после правки мастера (то, что реально собрали)
    lesson.md     «что поправил и почему» + обобщённое правило
```

### spec.md — что говорит чертёж

Только факты чертежа, без решений по сборке. Что не указано на чертеже — написать «не указано», не додумывать.

- изделие: обозначение, название, партия (`partQty`);
- провода: марка, сечение, цвет, длина (с допуском), количество, концы (А/В);
- контакты и терминалы: артикул, обжим или пайка, сторона;
- разъёмы и корпуса: артикул, распиновка, какие цепи в какие позиции;
- коаксиал: марка, тип разделки, центральный контакт, экран, корпус/крышка;
- маркировка: что, чем, где;
- термоусадка и защита: артикул, длина, позиция;
- требования: допуски, стандарт (IPC/WHMA-A-620…), особые условия.

### draft.json и final.json

Это сам `build_config` — объект из [схемы](build-config.schema.json), без обёрток и комментариев. Два файла всегда
пара: `final.json` получен правкой `draft.json`, а не собран заново.

### lesson.md — что поправил и почему

1. **Что поправили** — список по пунктам, каждый указывает на операцию или блок (по номеру в `ops[]` или `key` блока).
2. **Почему** — причина по-технологически, одним-двумя предложениями.
3. **Правило** — обобщение, применимое к другим чертежам: «если на чертеже X, то Y», а не «в этом чертеже было так».
   Правило без условия («всегда делать Z») писать только если мастер сказал именно так.

Если мастер ничего не менял — так и записать: «черновик принят без правок»; такой образец тоже ценен.

## Именование

- `<drawing-id>` — обозначение чертежа/изделия как в документации, нижний регистр, латиница и цифры, слова через
  дефис: `kb7-provod-300`, `p-300-kb12`. Кириллицу в имени папки не использовать; русское название — в `spec.md`.
- Одно изделие — одна папка. Новая редакция чертежа — новая папка с суффиксом `-r2`, старая остаётся.
- Файлы называются ровно `spec.md`, `draft.json`, `final.json`, `lesson.md`; JSON — UTF-8, переводы строк LF.
- Кодировка и язык: тексты для людей — по-русски; ключи JSON — как в схеме.

## Корпус в базе ERP

Корпус будет жить и в базе ERP (через API): образцы пишут и читают из ERP, поле `lesson` выводится рядом с парой
«черновик — итог». Эта папка — выгрузка из базы (export): после появления API образцы из ERP выгружаются в
`docs/assembly-corpus/<drawing-id>/` в том же формате, а файлы отсюда можно загрузить в базу. Формат файлов не
меняется, поэтому оба пути взаимозаменяемы. Пока API нет, папка — единственное хранилище.

## Проверки

`backend/tests/techcards/test_build_config_schema.py` проверяет, что схема принимает все ручные конфиги из
`test_etk_manual.py` и отвергает то, что отвергает движок. Расширять схему (типовые операции генератора в ручной
сборке) — через ветку `generatorOperation` в `$defs.operation`.
