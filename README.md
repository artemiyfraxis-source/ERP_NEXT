# Fraxis ERP Next

Новый контур ERP развивается параллельно с действующим SUPPLYMAP и локальным
зеркалом работающей ERP.

Главное правило миграции: переносим предметные правила, а не GAS-файлы и не
структуру Google-таблиц.

- Все модули принадлежат SUPPLYMAP и переписываются нативно. «Проекты» — производственные проекты,
  заводятся из расчёта (SUPPLYMAP `TcKitset.gs`). Реестр проектов и «Расчёт и КП» старой ERP вне переноса:
  это другой блок (решение владельца 29.09.2026).
- `System ID` сохраняется в поле `legacy_id` для сверки и импорта, но не
  становится первичным ключом новой базы.
- Google Sheets остаются переходным источником данных, а не новой архитектурой.

Текущая архитектура и порядок переноса описаны в [ARCHITECTURE.md](ARCHITECTURE.md).

## Нативный модуль техкарт

```powershell
npm run sync:techcards
npm run sync:techcard-library
cd backend
py -m venv .venv
.\.venv\Scripts\pip.exe install -r requirements.lock.txt
.\.venv\Scripts\alembic.exe upgrade head
$env:ERP_DATABASE_URL = "postgresql+psycopg://..."
.\.venv\Scripts\python.exe -m app.modules.techcards.seed_library
.\.venv\Scripts\python.exe -m pytest tests -q
```

Импортируются чистые сервисы генерации маршрута и их исходные тесты из ветки
`feat/techmap-web-generator`. API модуля нативно расширен карточками проектов, выдачей ЭТК и журналом ревизий по контракту `docs/briefs/electronic-techcards.md`. В `backend/app/modules/techcards/SOURCE.json`
записывается точный commit; изменения генератора сначала делаются в его ветке,
после чего модуль синхронизируется повторно.

Библиотека типовых операционных карт синхронизируется отдельно из актуального
SUPPLYMAP. Скрипт принимает `SUPPLYMAP_SOURCE_REPOSITORY` и `SUPPLYMAP_SOURCE_REF`,
поэтому умеет забирать ещё не опубликованную локальную ветку без копирования файлов вручную.
В ERP хранится исходный снимок строк без потерь и разобранные
поля операций, оснастки, требований безопасности и дефектов. Импорт в БД
атомарно заменяет всю библиотеку и повторный запуск безопасно пропускает уже
загруженный commit.

`POST /api/techcards/projects/{id}/build` собирает ЭТК нативно из config
генератора и текущей библиотеки, сохраняет внутри документа снимки карточек,
материалы, входы, результаты, времена и точный commit источника. Перед сборкой workflow
подтягивает из версионного снимка БД.Технология аппликатор, высоту обжима и pull-test по артикулу
терминала и сечению провода; отсутствующие нормы остаются явными предупреждениями. Совместимость
проверяется на семи живых config из SUPPLYMAP, включая резку с обжимом. Нативный сборщик
также понимает отдельную разделку кабеля под пайку/сростки, роторную резку, терминал и
аппликатор в `CUT_WIRE+1crimp`, строит схему ветвей через узел сростков и запрещает выдачу
карты с резкой без длины. Для известных семейств JST, Molex, TE, Connfly, Amass, RJ45,
Weipu, CNLINKO, USB-A и штекеров «банан» API вычисляет вид корпуса со стороны проводов; React показывает нумерацию
и занятие контактов, не изменяя сохранённый снимок ревизии. В интерфейсе ЭТК показана
операционными карточками, а библиотека из 115 шаблонов доступна для поиска и
структурированного просмотра без чтения исходного JSON.

Legacy-диагностики листов `diagEtkCoverage`, `diagTcDropIssued` и сопоставление
`INS_MARK_HARNESS` с именем Google Sheet отдельно не переносятся: нативная карточка
не может перейти в `ISSUED` без сохранённого документа ЭТК, а операций удаления
выданной карты и связанных Drive-файлов в ERP_NEXT нет. Эти проверки заменены
инвариантом агрегата и тестами, а не опасной обслуживающей ручкой.

Импорт TECHMAP-GRAPHER принимает `.techmap-project.zip` или `project/snapshot.json`,
проверяет schemaVersion, объединяет одинаковые провода, сохраняет кабель как одну
строку с числом жил и переносит длину по чертежу и разделку оболочки в config.
Поправки концов и длина реза из чертежа остаются рядом как проверяемые исходные
данные; припуски по L+/L− и рабочий маршрут по-прежнему считает нативный генератор ERP.

## Нативный модуль заявок

Первый предметный срез находится в `backend/app/modules/requests`. Он уже
переносит обязательные поля SUPPLYMAP, разделение «назначение / проект», правила
категории и документа качества, расчёт приоритета и суммы, совместимый
`legacy_id`, номера назначения и контракт передачи в закупку.

Ручки `GET /api/requests/schema` и `POST /api/requests/validate` ничего не
записывают. `POST /api/requests` создаёт пачку по обязательному заголовку
`Idempotency-Key`, а `POST /api/requests/handoff` доступен только ролям
`buyer/admin` с правом `procurement:edit`. Инициатор всегда берётся из серверной
auth-сессии.

SQLAlchemy Unit of Work одним commit сохраняет агрегаты, audit и outbox.
SQLite используется только интеграционными тестами; эксплуатационный URL —
PostgreSQL через Psycopg 3. Без действующей Identity-сессии ручки отвечают
`401`, без права `edit` — `403`, а без `ERP_DATABASE_URL` — `503`.

Повтор сетевой команды передачи должен возвращать прежний результат по
`idempotency_key`. Создать новую закупочную ревизию сможет только отдельная
business-команда retransfer — обычный retry не размножает строки.

## Нативный модуль закупок

`backend/app/modules/procurement` владеет своей строкой, статусами и ревизией.
Outbox-consumer идемпотентно создаёт строку `Новый / A`; закупщик через
`/api/procurement/available` берёт её в работу, видит свои строки в
`/api/procurement/mine` и сохраняет факты через `PATCH /{id}/facts`. При наличии
поставщика, точки доставки, положительного фактического количества и единицы
строка сразу становится `Готов к запросу`. Роль с доступом «просмотр» (ID-6) читает
`/available` и `/api/procurement/in-work` (строки всех закупщиков в работе), но ничего не пишет.

Фоновый consumer запускается отдельным процессом:

```powershell
cd erp\backend
.\.venv\Scripts\python.exe -m app.outbox_worker
```

Для cron/диагностики доступен однократный запуск `-m app.outbox_worker --once`.
Раз в минуту воркер в отдельном потоке добирает пустые наименования наборов «Проектов» с сайтов
поставщиков по ссылкам из расчёта (`tcKitNamesTick_`, не больше 15 страниц за раз): ему нужен
исходящий HTTP(S) в интернет; адреса внутренней сети не запрашиваются.
Создание закупочной строки, audit и отметка outbox как обработанного происходят
одной транзакцией.

После заполнения строки закупщик фиксирует запрос поставщику, затем счёт и
ожидаемую дату, затем оплату. Оплата переводит строку `В пути` и транзакционно
создаёт `receiving.expected`.

## Приёмка и склад

Нативные разделы `/api/receiving` и `/api/stock` доступны ролям
`receiver/admin` с правом `edit`. Приёмка повторяет последовательный входной
контроль SUPPLYMAP, выдаёт ГРН, требует адрес физического размещения и только
после этого публикует приход. Склад учитывает партии по `склад + ГРН + пакет`,
но товар внутри партии определяет по артикулу. Наименование хранится отдельно
как необязательное человеческое описание, серия изготовителя — отдельно от
внутреннего ГРН. Старые наименования миграция переносит в артикул без изменения
остатков. Поиск и подбор партии для комплектации используют артикул первым.
Склад разделяет баланс и резерв, поддерживает из одного окна перемещение отдельной
партии или всего физического места и списание с обязательным основанием. При
переносе места вложенные ячейки `A…Z` сохраняются, партии с нулевым остатком не
двигаются. Все переходы используют optimistic version и пишут
audit в той же транзакции.

Ручное внесение фактически посчитанных остатков выполняется через
`POST /api/stock/batches`. Номер партии выдаётся транзакционной годовой
последовательностью, поэтому параллельные операции не создают одинаковые ГРН.
Артикул обязателен; наименование и серия могут быть добавлены или исправлены
позже без замены ГРН и без изменения количественного учёта. Форма сначала
подставляет пустые поля по уже внесённым партиям, затем — по версионному снимку
БД.Технология, семействам корпусов и правилам кодов коаксиальных разъёмов; подсказку
всегда можно исправить вручную. Цифровые артикулы остаются строками и не теряют
ведущие нули.
Точечное исправление карточки отправляет ожидаемую версию партии: если артикул или
другие данные уже изменились после открытия формы, сервер отклоняет устаревшую запись.
Повторные партии одного артикула в списке сшиваются в одну строку и раскрываются
до ГРН; пустая старая строка получает временный ключ по ГРН и тоже раскрывается для
исправления артикула. Поверх этого доступны группировки по типу, полке, наименованию и серии.

Раскладка стеллажей (SK-9): место при приёмке, быстром вводе, перемещении и переносе места должно
существовать — стеллаж не больше их числа, полка в пределах своего стеллажа, № на полке до 999, иначе
«Места … нет: проверь номер стеллажа и полку.». По умолчанию раскладка как живая в SUPPLYMAP: 32 стеллажа,
полки A…Z. Другую задают JSON в `ERP_WAREHOUSE_RACK_LAYOUT` (тот же, что `stock05_places` в Script
Properties SUPPLYMAP), до запуска backend:

```powershell
$env:ERP_WAREHOUSE_RACK_LAYOUT = '{"racks": 20, "shelves": 26, "perRack": {"5": 12}}'
```

Раскладку, сохранённую с экрана склада «Раскладка» (хранится в базе), система берёт раньше переменной окружения.

Битое значение останавливает запуск. Пустое место и старый адрес «как есть» (импорт, ручная правка места)
раскладкой не проверяются.

«Оформить заявку» → «Из расчёта» (как `openCalc`/`extractFromCalc` в SUPPLYMAP): оператор вставляет ссылку на
Google-таблицу расчёта, сервер читает лист «ЗКП» (A:T, отображаемые значения) и «ЗКЗ»!B2 через Google Sheets
API v4 от имени сервисного аккаунта Google. Ключ задаётся в `ERP_GOOGLE_SERVICE_ACCOUNT_JSON` — JSON-ключ
целиком или путь к файлу ключа (Google Cloud → IAM → Service Accounts → Keys → JSON; в проекте включить
Google Sheets API). Каждую таблицу расчёта нужно открыть на чтение («Читатель») для e-mail сервисного аккаунта
(`client_email` из ключа) — иначе ERP так и отвечает, называя этот e-mail. Без переменной `POST
/api/requests/import/calc` отвечает `503` с подсказкой, а в UI остаётся запасной путь — вставить диапазон листа
ЗКП вручную (`/api/requests/import/parse`). Новых пакетов не нужно: вход по JWT (RS256) сделан на `httpx`.

```powershell
$env:ERP_GOOGLE_SERVICE_ACCOUNT_JSON = 'C:\secrets\erp-calc-reader.json'
```

### Импорт живых остатков из SUPPLYMAP (WH-IMPORT)

Выгрузка склада (`ЦАР.csv`, `ЖУК.csv`, `СПИСАНИЕ.csv`, `_manifest.json` из `whExportRead`) лежит в
`data/import/` — папка в `.gitignore`, это живые данные. Импорт берёт базу из того же `ERP_DATABASE_URL`,
что и приложение (схема уже накатана `alembic upgrade head`):

```powershell
cd backend
$env:ERP_DATABASE_URL = 'postgresql+psycopg://USER:PASSWORD@HOST:5432/erp_next'
.\.venv\Scripts\python.exe -m app.modules.warehouse.import_stock --dir ..\data\import --dry-run
.\.venv\Scripts\python.exe -m app.modules.warehouse.import_stock --dir ..\data\import
```

`--dry-run` проходит тот же путь в транзакции и откатывает её: печатает отчёт сверки и ничего не пишет.
Отчёт сверяет БАЛАНС по складу и единице измерения и по каждому ГРН с партиями ERP до единицы, перечисляет
отклонённые строки с причиной, расхождения журнала СПИСАНИЕ со СПИСАНО и колонки, которые пока не
переносятся. Повторный запуск с теми же данными ничего не создаёт и не меняет. Код выхода: 0 — всё сошлось,
1 — есть отклонённые или расходящиеся строки, 2 — выгрузка не читается или не задан `ERP_DATABASE_URL`.

### Загрузка баз «Технологии» из зеркала (REF-MIRROR-LOAD, REF-MIRROR-ALL)

Читает зеркало `_local/db/*.tsv` репозитория SUPPLYMAP (только чтение; путь — `--source` или
`SUPPLYMAP_SOURCE_REPOSITORY`, иначе соседняя папка `SUPPLYMAP`) и одной транзакцией заменяет в снимке
справочников БД.ОБ, БД.ОП, БД.ТЕР, БД.КОАКС, БД.ПРОВ и БД.МАТ (все шесть файлов обязательны) и, если есть
`СПР.КАБ.tsv`, обе таблицы СПР.КАБ. Записи ОБ/ОП/ТЕР/КОАКС получаются те же, что даёт GAS-выгрузка через
`PUT /tech-operations/supplymap-snapshot` (включая диапазоны AWG/мм² терминалов для подбора норм обжима);
дата исходника снимка — последняя `pulledAt` этих листов в `_local/db/_meta.json`. Правки строк, сделанные в
ERP после прошлой загрузки, заменяются зеркалом.

```powershell
cd backend
$env:ERP_DATABASE_URL = 'sqlite:///preview.db'
.\.venv\Scripts\python.exe -m app.modules.references.load_mirror --dry-run
.\.venv\Scripts\python.exe -m app.modules.references.load_mirror
```

`--dry-run` печатает дату выгрузки и число строк в зеркале и в снимке по каждой базе и ничего не пишет.
Код выхода: 0 — готово, 2 — файла нет, он не таблица или база без единой записи (шапка не распознана), либо
не задан `ERP_DATABASE_URL`. Свежесть зеркала — забота SUPPLYMAP (`npm run db:pull` в `_local/tooling`).

## Комплектация и выдача в цех

Нативный раздел `/api/issues` создаёт заявку на комплект даже при отсутствии
остатков; пустой BOM остаётся единственным случаем без заявки. Потребность и
резерв хранятся раздельно. Конкретную складскую партию выбирает сотрудник, а не
FIFO-алгоритм: доступная партия привязывается к строке и резервируется в общей
транзакции склада и комплектации.

Статус `Готов к выдаче` возможен только для полностью зарезервированного
комплекта. Команда выдачи атомарно списывает весь комплект из резерва; частичная
выдача не допускается. Инженер и кладовщик комплектуют, мастер и начальник
производства видят состояние, а физическую выдачу подтверждает кладовщик.
После производства кладовщик принимает комплект на место возврата и по каждой
позиции фиксирует годное, возвращённый брак и невозвращённый брак. Только годное
сторнирует складское списание; неизрасходованный остаток считается явно, а не
теряется при закрытии заявки.

## Производство и прослеживаемость

Первый слой `/api/production` переносит планирование из `ProdTasks.gs`: мастер
запускает задание со снимком маршрута выданной техкарты, назначает нескольких
операторов на одну операцию и получает план по календарю 09:00–17:30 с обедом.
Автоплан учитывает занятость, праздники и отсутствия и ищет первое общее
свободное окно. Ручной старт разрешён, но конфликт возвращается предупреждением.

У операции намеренно нет собственного статуса: он вычисляется по фактической
выработке. Отмена задания сохраняет маршрут, назначения и план как историю;
задание можно вернуть в работу. Оператор видит только назначенные ему операции.

Второй слой добавляет рабочие сессии и коробки. Оператор берёт подтверждённые
коробки предыдущего этапа, система атомарно резервирует количество, а при
завершении создаёт неизменяемую запись выработки и связи расхода между входной и
выходной коробками. Пауза учитывается отдельно; отмена текущей работы снимает
резервы. Каждая коробка имеет шестизначный последовательный номер с контрольной
цифрой. После закрытия оператором мастер подтверждает коробку либо возвращает её
с обязательной причиной; только подтверждённая коробка доступна следующему этапу.
Первая операция получает вход только из выданной заявки комплектации: оператор
выбирает конкретные позиции с сохранёнными ГРН и номером пакета. Последняя
подтверждённая коробка принимается кладовщиком прямо в соответствующую позицию
реестра ГП; система присваивает/сохраняет ГРН `ГП` и записывает связь от коробки.

Брак не смешивается с годной коробкой. При записи выработки оператор обязательно
указывает характер и описание; система создаёт изолированную брак-коробку серии
`Б-000001-8`. Мастер выбирает «Доработка», «Списание» или «Использовать как есть»
и указывает акт/основание. Решение дописывается отдельной строкой и не заменяет
исходный факт брака.

Для каждой штуки задания резервируется серийный номер формата
`ПЗ-0001-0001`. ОТК принимает только последнюю подтверждённую коробку, делит её
на годные и изолированный брак и привязывает серийные номера. Отклонённое ОТК
количество вычитается из доступного остатка коробки и физически не может попасть
в ГП. Забракованная ОТК партия остаётся в отдельной очереди мастера; решение
«Доработка», «Списание» или «Использовать как есть» записывается один раз с
актом/основанием и не меняет исходный протокол контроля. Роль `qc` отделена от
оператора. Реестр СИ хранит инвентарный номер и срок
поверки; просроченное или выключенное СИ сервер не принимает в контроль.

Поиск «Прослеживаемость» принимает серийный номер, номер коробки, входной ГРН
комплектующего или ГРН готовой продукции и возвращает весь связанный граф:
`ГРН+пакет → коробки операций → серийные номера → ГРН ГП`. Граф строится из
неизменяемых рёбер расхода, поэтому не зависит от текущего экрана или статуса.

Нативный «Производственный план» переносит `ProdPlan.gs`: одна строка на проект с КБ,
вычисляемый этап по фактам ТК/комплектации/работы/ГП/отгрузки, сводка снабжения и назначений,
дни до дедлайна и журнал блокеров/комментариев. Для каждой КБ мастер может временно заменить
вычисленный этап ручным либо вернуть режим «авто», а проверка ТК имеет состояния «не проверена»,
«проверена» и «с погрешностями» с обязательным описанием. Новая ревизия ТК делает более старую
отметку проверки неактуальной. Журнал append-only; текущий блокер и дедлайн выводятся
из истории. Внешний реестр проектов может передать заказчика, дату и терминальный статус атомарным
снимком `/api/production/plan/projects-snapshot`; без него план строится из нативных проектов и техкарт.

## Готовая продукция и отгрузка

`/api/shipping` переносит реестр `ГОТОВАЯ ПРОДУКЦИЯ` и очередь заявок из
`Shipment.gs`. Отдельного склада ГП нет: каждая КБ проекта хранит «принято» и
«отобрано», остаток вычисляется как их разница. Первый приём получает собственный
ГРН серии `ГП.ГГ.NNNNNNN`; следующие сдачи той же КБ увеличивают принятое по
тому же ГРН.

Менеджер создаёт заявку с получателем, снимком адреса, условиями доставки и
данными УПД. Заказанное количество не ограничивается текущим остатком. Кладовщик
набирает `min(недобор, остаток)`, поэтому в строке раздельно хранятся заказанное,
набранное и недобор. Отмена до отправки возвращает весь набор в реестр ГП.

Упаковка выдаёт номера PL/DN по проекту. Генерация файлов из Google Docs пока не
перенесена. Сервер не разрешает отправить бумажную поставку без файла УПД, а
закрыть заявку — без номера и файла УПД, даты отправки и трек-номера для ТК.

## Справочники и база техопераций

`/api/references` разделяет два разных вида данных из SUPPLYMAP. Карты
«домен ссылки → поставщик» и «изготовитель → страна» редактируются вручную и
заменяются целиком одной транзакцией. Домен поставщика нормализуется без
протокола, `www` и пути; имя изготовителя сравнивается без учёта регистра и
лишних пробелов. Повтор нормализованного ключа отклоняется до записи.

`БД.ОП`, `БД.ОБ`, `БД.ТЕР` и `БД.КОАКС` хранятся отдельно как версионированный
снимок. API импорта принимает номер схемы, дату исходника и записи, а рабочий
экран даёт поиск по отображаемому тексту и семантическим полям. Снимок заполняется
из зеркала SUPPLYMAP командой `python -m app.modules.references.load_mirror` (раздел
«Загрузка баз «Технологии» из зеркала» выше) или GAS-выгрузкой через
`PUT /api/references/tech-operations/supplymap-snapshot`. Изменять карты
и заменять снимок может только администратор; остальные рабочие роли получают
доступ на чтение.

## Журнал, фоновые задания и уведомления

`/api/notifications` — персональная лента: адрес получателя берётся только из
Identity-сессии, поэтому запрос не может прочитать или отметить чужие события.
Доставка из `notification.requested` выполняется тем же отдельным outbox-worker,
идемпотентна по событию и адресату и не откатывает уже совершённую бизнес-операцию.
Портальная лента остаётся основным каналом; SMTP-дублирование не включено.

`/api/operations/audit` показывает руководству и администратору неизменяемые
события всех нативных модулей. `/api/operations/outbox` показывает обработанные,
ожидающие и dead-letter сообщения и последние ошибки. Старый минутный
`OwnerTick` не воспроизводится: переносы статусов и данных уже происходят в
транзакциях команд, а worker занимается только асинхронной доставкой. Бэкап БД
должен выполняться средствами инфраструктуры PostgreSQL, а не кодом ERP.

## Identity и доступ

Нативный Identity хранит стабильный UUID сотрудника, роль и персональные права
разделов `view/edit`. Персональная настройка сильнее ролевой; отсутствие права
закрывает раздел. Пароли защищены Argon2id, сырой session token в БД не хранится.
Браузер получает `HttpOnly + SameSite=Strict` cookie (в HTTPS — с префиксом
`__Host-`), а любые записывающие
запросы с cookie требуют `X-CSRF-Token` из cookie `erp_csrf`. Сессия скользящая
на 14 дней, но имеет абсолютный предел 30 дней; деактивация сотрудника отзывает
все его сессии одной транзакцией.

После миграции первого администратора создают интерактивно — пароль не попадает
в аргументы процесса или историю shell:

```powershell
cd erp\backend
$env:ERP_DATABASE_URL = 'postgresql+psycopg://USER:PASSWORD@HOST:5432/erp_next'
.\.venv\Scripts\python.exe -m app.identity_admin create-user `
  --login admin --email admin@example.local --name "Администратор" `
  --department "Администрация" --role admin
```

Остальных сотрудников администратор заводит и правит на экране «Сотрудники»
(раздел «Данные»): ФИО, отдел, место работы, роль, вход вкл/выкл и пароль, который
задаётся там же и никогда не возвращается в ответах; там же ведётся список отделов.

На локальном HTTP дополнительно задайте `$env:ERP_COOKIE_SECURE = '0'`. В HTTPS
оставляйте значение по умолчанию. Reverse proxy должен передавать доверенный
адрес клиента и дополнять встроенный лимит тела (1 МиБ) сетевым rate limit.

`npm run check` запускает архитектурные Node-тесты, весь backend через локальный
`backend/.venv`, UI-тесты и production-сборку React. Переменная `ERP_PYTHON`
позволяет CI явно указать Python.

## База данных

```powershell
cd erp\backend
$env:ERP_DATABASE_URL = 'postgresql+psycopg://USER:PASSWORD@HOST:5432/erp_next'
.\.venv\Scripts\alembic.exe upgrade head
cd ..\frontend
npm ci
npm run build
cd ..\backend
.\.venv\Scripts\uvicorn.exe app.main:app --host 127.0.0.1 --port 8021
```

После сборки FastAPI отдаёт React-оболочку по `http://127.0.0.1:8021/`; API
остаётся под `/api`. В режиме разработки UI можно запустить отдельно командой
`npm run dev` в `erp\frontend` — Vite откроется на порту 5176 и проксирует API
на 8021.

Приложение не создаёт таблицы само. Схема меняется только миграциями Alembic:
первая создаёт `requests`, `audit_events` и `outbox_messages`, вторая —
`procurement_lines`, третья — пользователей, права и сессии Identity, четвёртая —
поток счёта/оплаты, `receiving_lines` и складские партии `warehouse_lots`.
Пятая добавляет безопасную последовательность ручных складских партий, шестая —
заявки комплектации, их строки и привязки к партиям, седьмая — результаты
возврата комплекта и брака, восьмая — задания производства, снимки маршрутов,
назначения и календарь цеха. Девятая создаёт готовую продукцию и отгрузки,
десятая — карты справочников и снимок техопераций, одиннадцатая — персональные
уведомления и доступ к операционному журналу, двенадцатая — рабочие сессии,
коробки, неизменяемую выработку и связи производственного расхода, тринадцатая —
вход первой операции из выданных ГРН и сдачу последней коробки в ГРН готовой
продукции. Четырнадцатая добавляет ограничения конкурентного старта: у оператора
не может появиться две текущие работы или две открытые коробки одной операции.
Пятнадцатая создаёт изолированные записи брака и неизменяемые решения по ним.
Шестнадцатая добавляет серийные номера, ОТК, реестр СИ и отсечение брака ОТК от
остатка, который разрешено сдать в готовую продукцию.
Семнадцатая хранит append-only решения по браку ОТК, восемнадцая — карточки проектных ЭТК и ревизии,
девятнадцатая — атомарную библиотеку операционных карт, двадцатая — проекцию реестра и append-only журнал
производственного плана, двадцать первая — смену цеха и матрицу компетенций для авторасчёта заданий,
двадцать вторая — отдельные артикул/описание/серию склада, двадцать третья — структурированные
ручные этапы КБ и отметки проверки техкарт.
